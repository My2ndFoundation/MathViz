## 3a 用血换来的五条判断（这些比计划本身更重要）

### 1. "拿原生 JS 当参照"这个方法，比任何手写的期望值都值钱

词法器审查用它抓出 **5 条 Critical**——`1e10` 被切成 `[1, "e10"]` 两个 token、`0x1F` 切成 `[0, "x1F"]`、`'A'` 静默变成 `"u0041"`——而上一个会话手写的 21 条测试**一条都没覆盖到**。最终审核用同样的方法构造 105 组对照，又找出 10 组不一致。

这类缺陷的共同形态是**程序照样跑、只是算出别的东西**，正是规格 §9 点名的「半懂不懂的解释器比明确拒绝更危险」。

**3b 里凡是能与原生/与既有实现对照的，就别写死期望值**（编辑器高亮片段拼回原文、检查器报的行列、游标的深度判据）。

### 2. 测量方法本身可能就是 bug

上一个会话给 3a 的深度探测脚本，探测值**全部大于 `MAX_DEPTH`**——我们自己的守卫必然先触发、全报 clean。**那条探测在原理上就测不到它要测的东西。** 执行者把守卫抬到 100000 绕开，才测到真实崩点。

仓库阶段 0 栽过同一类：用离屏紧循环测绘制耗时得出"65 倍余量"，而那个方法在原理上就观测不到合成。

**看到一个测量结果之前，先问它测的到底是什么。**

### 3. 测试全绿 ≠ 它有牙

3a 最终审核做了 36 次变异，**15 次没变红**，其中沙箱的三条核心保证（不走原型链读、`setProp` 黑名单、`const` 不可重新赋值）**一条都没被钉住**——空白形态是"**压根没写断言**"，不是"写了拦不住"。

**凡是注释里郑重声明"这条很重要"的性质，去查它有没有对应的断言。** 改坏实现看测试会不会红，是最便宜的验证。

### 4. 视觉与交互缺陷，能读代码的东西抓不到

阶段 0–2 里用户三次截图，各抓出一个多轮代码审核都漏掉的问题（相机偏 83°、棋子不随缩放、控件语义错置）。

3b 有验收页正是为此。**把"请你看一眼"当成正式验收环节，不是可选项。**

### 5. `_test.js` 的 `eq` 有一个假阴性陷阱

`_test.js` 的 `eq` 用 `JSON.stringify` 比较，而 **`JSON.stringify(function(){})` 与 `JSON.stringify(undefined)` 都是 `undefined`**。于是 `T.eq(某个泄漏出来的函数, undefined)` **会通过**。

3a 的沙箱断言最初正是这个形态，靠变异往返才发现。**要断言"某值不存在"，用 `T.ok(typeof x === 'undefined', …)`。**

**其余四个测试文件里的同类形态待 triage**——这是一条留给你的、可以顺手做掉的事。

## 环境事实（会浪费你时间的那些）

- **浏览器面板的 rAF 被节流到约每十二秒一帧**，`document.hidden` 恒为真。**"我看了几秒没动"什么都证明不了**；截图可能是十几秒前的旧帧。**要验状态就读探针，要验时序就直接推累加器。**
- **预览服务器**是 `.claude/launch.json` 的 `mathviz`（8777 端口，**根在主 checkout 而非 worktree**）。所以**需要浏览器验收的任务不要放进 worktree**——在 worktree 里没法验自己写的页面。用 preview 工具启动，不要用 Bash 起服务器。
- **多 agent 共享浏览器会话，每次调用带显式 `tabId`**，先 `tabs_context` 确认。3a 里有一次未指定 `tabId` 的截图落到了别的 agent 的标签页上（只读，无损，但换成 `javascript_exec` 就是把测量归错了页面）。
- **开发者的外接显示器是 30Hz**（已从显示器菜单确认）。一切按 `dt` 推进，**绝不按帧计数**，否则在他机器上慢一半。用 `VizEngine.state.dt`。
- **性能预算是每帧绘制耗时 ≤4ms**，不是 fps——fps 门槛量的是显示器不是代码。强制光栅化**每帧只做一次**，探针开销单列并排除（这个错误曾把 0.30ms 放大成 6.00ms）。
- **简报放在 `.superpowers/`，那是 repo 级 gitignore**——worktree 里没有。给 agent **绝对路径只读**，报告让它写在**自己 worktree 内**，跨界搬运由你做。
- **两个 agent 不能同时改同一个文件**——同一 checkout 里它们会互相覆盖，这不是 git 冲突，是纯粹的丢工作。

## 3b 特有的坑（可预见的四个）

### 1. 变量面板的「深度窗口回放」（计划里的约束 1）

本阶段**最容易做错、也最容易"看起来对"**的地方。

3a 的 `varDelta` 只带 `{ name, from, to }`，**不带作用域标识**。递归时同名参数在各帧各有一份，**全局按名扁平回放会跨帧串味**。轨迹里的信息是够的（`depth` / `frameOp` 划得出帧区间），**但消费方必须正确使用它**。

**阶段 5 的六道算法题全是递归**——这条错了，那六道题的变量面板全是错的，而且是"显示一个错的数字"这种最难被发现的错法。

计划里有一条专门拿 `fact(3)` 钉它的测试，**别放过它**。

### 2. 浏览器里必须重测递归深度崩点（约束 3）

`MAX_DEPTH = 500` 是**在 node 下**校准的（冷启动约 674 层引擎抛裸 `RangeError`，留了约 26% 余量）。

**但解释器的真实部署环境是浏览器**（内联进 `tools/*.html`），浏览器对嵌套生成器的栈深度未必与 node 一致。**3b 是第一个有页面可以跑的阶段。**

若浏览器里出现裸 `RangeError`，**停下来报告**——那意味着 `MAX_DEPTH` 要跟着降，是需要用户裁定的事。

### 3. 约束 6 建议**最先**做

把 `hoistLexicalDecls` + `hoistFunctionDecls` 抽成共用前置。3a 最后一个缺口的根因就是 `callInterpreted` 与 `evalBlockBody` **两套语句循环各自维护前置**——当时只给其中一套接了 TDZ，函数体顶层的前向引用就绕过去了。

不做的话，下次往前置里加东西会以**完全相同的方式**再漏一次。

### 4. 验收页的示例程序规模

必须在 `STEP_LIMIT = 200000` 之内。实测参考：

| 程序 | 步数 |
|---|---|
| N 皇后 N=6 | **4,674**（原写 4,370 有误，3b 实施时实测更正） |
| N 皇后 N=8 | 73,904 |
| Warnsdorff 骑士巡游 5×5 / 6×6 | 3,523 – 5,670 |
| **朴素回溯 DFS 骑士巡游 5×5** | **472,717**（超限） |
| **朴素回溯 DFS 骑士巡游 6×6** | **13,393,996**（GB 量级轨迹，架构装不下） |

轨迹每步约 426 字节。`STEP_LIMIT` **是架构上限，不是可调旋钮**。
