### R11  —— T3 评审发现 ③，与计划文本冲突

计划 T3 的实现说明白纸黑字给了
`/\bid=(\S+)/` 与 `/\blevel=(\S+)/`，而评审员复现出
`# >>> BLANK hint="see id=5 example" id=real level=2 hintEn="y"` 会把 id 解析成 "5"。
**采纳发现、推翻计划的那两条正则**：改为**先摘掉 hint="…" / hintEn="…" 两段带引号的属性，
再在剩余文本上匹配裸值**。 — 理由：计划自己允许属性任意顺序，所以"截取第一个 hint= 之前"
也不成立；摘掉引号段是唯一同时满足"任意顺序"与"不被引号内文本污染"的做法。

— 代价：若某天有人想在裸值里写引号，这个预处理会碍事；但裸值按定义读到空白为止，
本来就不含引号。计划正文同步订正。


### R12  —— T1 偏离 brief ①，控制方已用 CPython tokenize 独立复核

**采纳**

### R13  —— T1 偏离 brief ②

**采纳**"未闭合单引号串止于行尾，三引号仍吃到文件尾"。
CPython 对未闭合串直接抛 TokenError，没有标准可依，所以这是一个设计选择而非对齐。
止于行尾把一个打了一半的引号的破坏限制在一行内；吃到文件尾会让下面整篇失色——
正是 chess 整篇降级的同一种代价，而本模块的全部理由就是绕开它。 — 代价：一个真正
跨行的单引号串（不合法 Python）会被切成两段，无实际影响。

### R19  —— T5 顾虑 4，控制方实测确认

PEP 701——本机 Python 3.12.9 把 f-string 切成
`FSTRING_START` / `OP` / `FSTRING_MIDDLE` / `FSTRING_END`，3.11 及以前是单个 `STRING`。
本章十条 f-string 是这道门的主力语料，所以它天然是"本地绿 / CI 红"家族的一员。
门必须**两种形状都处理**（3.12+ 把 START..END 合并成一个区间；≤3.11 直接用那个 STRING），
并且**每次运行都打印它跑在哪个 Python 版本上**；CI 里 pin 一个版本。
 — 代价：门的代码多一个分支；不做则 CI 上会出现一片与真实缺陷无关的红。


### R20  —— T1 修复轮带回的情报，给 T14

`lex_vs_cpython_check` 的装饰器合并逻辑
**必须自己跟踪括号深度**。CPython 在括号内**照样发 `NL` token**，所以「上一个 token 是
NL/NEWLINE」**不等于**逻辑行首——T1 的实现者第一版探针就是这么写的，结果把括号内
换行后的 `@b` 并成了装饰器，对着一个正确的词法器报了红。
 — 理由：这是实测撞出来的假阳性，不是推测；一道会误报的门比没有门更糟，它会训练人忽略红灯。
 — 代价：门的代码多一个深度计数器；不做则 numpy 风格的多行表达式会批量误报。


### R21  —— T5 修复轮带回，R16 的副作用一

`.py` 在 R16 之后不再保证 ASCII 可解码。
`build_programs.py` 与**每一道读 `.py` 的门**必须显式 `encoding='utf-8'`；
`program_embed_roundtrip_check()` 的逐字节比对两边必须同在 bytes 层或同在 str 层。
 — 理由：T5 的实现者自己的脚本当场炸了 UnicodeDecodeError，这是已发生的事实不是推测。
 — 代价：不做则 T10/T14 会在第一个带中文 hint 的章上崩，且崩在一个与真实缺陷无关的地方。


### R22  —— R16 的副作用二，控制方已独立复核

新增一道门 `source_bmp_check()`——
`.py` 里不许出现非 BMP 字符（码位 > U+FFFF）。CPython `tokenize` 给**字符**偏移，
JS 给 **UTF-16 码元**偏移，两者只在全 BMP 时相等；一个 emoji 让该行之后所有偏移
**静默平移且不报错**。实测：本章最高码位 U+FF1B、482 字符 == 482 码元（安全）；
构造 `x = 1  # 🚀` 立刻变成 17 字符 vs 18 码元。
 — 理由：与 R19 的 PEP 701 同属「静默错位」家族，而这一条今天只是运气好。
 — 代价：禁掉 emoji 提示语；相对于一整道门批量误报，这个代价可以忽略。
第 0 期的门数由 30 增至 **31**。


### R23  —— T1 评审 Important #1

`1e` 切成 `number:1` + `name:e` **是对的**（实测 CPython
给 `NUMBER '1'` + `NAME 'e'`），行为不改；但文件头与报告都写着「与 brief 的**两处**偏离」，
实际是**三处**——这才是缺陷。在一个把「documented, believed, and false」当作头号失败模式
的仓库里，一份少算自己的偏离清单本身就是那个失败，而且它绕过了控制方的裁决
（R12/R13/R14 三条能被判定，全靠它们被申报了）。
**同时把原则写下来**：`0x` 留在 brief 字面（`number:0x`）而 `1e` 对齐 CPython，看似不一致，
其实同一条规则——**CPython 有答案就对齐，CPython 抛错就自己选**。实测：`0x`/`0b` 抛
`invalid hexadecimal/binary literal`，`1e+` 抛 `invalid decimal literal`，`1e` 不抛。
这与 R12（raw 串反斜杠，CPython 有答案→对齐）和 R13（未闭合串，CPython 抛→自己选）
是同一条原则的第三、第四次应用。
 — 代价：只改注释与一条测试，行为零变化。


### R24  —— T1 评审 Minor #4，给 T14，控制方认定其重要性远高于 Minor


`lex_vs_cpython_check` 的比对**必须是双向的逐区间相等**，不能是「包含」。
评审员自己第一版探针只断言「CPython 的每个 token 起点也是 PyLex 的起点」，

要抓的头号缺陷。 — 理由：这是「一个在结构上无法观察到它声称排除之物的测量」，
本仓 CLAUDE.md 记过三次同类前科。 — 代价：不写明，T14 极可能造出一道假门。


### R25  —— T1 评审 Important #1 的下游情报，给 T14

CPython 对残缺字面量是 **raise**
而不是「给出不同答案」——实测 `0x`/`0b` 抛 `TokenError: invalid hexadecimal/binary literal`，

否则门死在参照实现那一侧，报出一个与被测代码无关的错。与 R15 的行续反斜杠同类。

### R28
