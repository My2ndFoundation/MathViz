## 0. 目标与受众

**受众**：16 岁，国际象棋**完全零基础**，即将开始 A-level Mathematics、Further Mathematics、Computer Science。

**目标不是提高棋力**，而是一条三段式路径：

1. **基本目的**：快速学会国际象棋的完整规则——一两个晚上从零到"读得懂题面、看得懂棋谱"。
2. **中间环节**：通过观看经典棋局，把规则从"记住的条文"变成"理解的东西"。
3. **最终目的**：**看懂与国际象棋相关的 CS 算法题，并学会自己设计算法去解这些谜题。**

第 3 条是全套工具的终点，它决定了工具 ④⑤ 不是动画而是**可编辑、可单步的算法调试器**（见 §1.4、§2.6–2.8），并最终落在**挖空练习**上（§2.9）——前面所有环节都是"看"，那是第一次"做"。

贯穿三段的手段是可视化——目的之一就是**靠"看得见"把兴趣先提起来**。

这条路径决定了全部设计取舍：规则层要**快而全**（不做低龄化动画，做能查能自检的参考级工具）；算法层要**对着考纲打**，而且必须让她能动手改。

### 与考纲的对应关系

| 棋盘问题 | 对应知识点 |
|---|---|
| 骑士巡游 | 哈密顿路径、启发式（Warnsdorff）|
| 车的最小覆盖 | 二分图匹配、König 定理（Decision Maths）|
| 王的最小支配集 | 支配集、贪心与最优的差距 |
| 八皇后 | 回溯、剪枝、状态空间搜索 |
| 马的最短路 | BFS、无权图最短路 |
| 博弈树 + α-β | 递归、对抗搜索、最好/最坏情况复杂度 O(b^(d/2)) vs O(b^d) |
| 王的移动距离 | 切比雪夫距离 L∞ 范数 |
| 香农数 | 指数增长、组合爆炸 |

## 1. 关键设计判断

### 1.1 为什么这套工具值得用 3D 引擎做

国际象棋是离散的，没有连续参数可以拖滑杆。但每个工具都有一个天然的**离散时间轴**，与引擎既有的 z 轴同构：

| 工具 | z 轴 | 顿悟视角看到什么 |
|---|---|---|
| ① 走法几何 | 最少步数场 | 马的场不是平移不变的：正相邻恒 3 步，而对角相邻在中心是 2 步、在角上是 4 步 |
| ② 规则与将杀 | ply（半步）| 将死 = 所有分支在某一层全部消失 |
| ③ 棋谱回放 | 回合数 | 一整局棋是三维里的一条曲线 |
| ④ 博弈树搜索 | 搜索深度 | α-β 剪掉的体积肉眼可见 |
| ⑤ 棋盘算法 | 递归深度 / 步序 | 回溯树沿 z 生长又缩回 |

所以这不是"把棋盘硬塞进 3D 引擎"，是真的合得上。

④⑤ 的 z 轴还有一层特殊含义：**它就是调试器里调用栈的深度**。栈长出去、树往 z 方向生长，是同一件事的两种画法。

### 1.2 独立子项目，但复用引擎

棋的状态是**离散、有分支、要撤销**的，与数学工具那套"共享 state + 连续采样"的模型硬绑在一起只会互相拖累。因此代码独立。但 3D 渲染引擎、设计令牌、UI 组件、i18n、录制回放框架全部复用（拷贝并裁剪）。

### 1.3 录制格式就是 PGN

设计系统 §11 主张"存轨迹，不存种子"。PGN 恰是这条主张的教科书例子——它存的是每一步的真实走法，而不是"初始局面 + 随机种子"。因此本子项目的录制格式**直接采用 PGN**，导出的存档可以丢进 lichess 打开。

### 1.4 算法工具是一台调试器，棋盘是它的输出窗口

工具 ④⑤ 不是"算法的动画"。它们是**单步调试器**：左边程序在跑、当前行高亮、调用栈随递归长出又缩回；右边棋盘上对应的格子同时被标成"正在尝试 / 已确认 / 被剪枝 / 回溯撤销"。两边是同一时刻的两种视图，而**驱动方是程序**，不是预先编排的动画。

这一条决定了整套工具的终点。规则与棋局是"看懂别人写的"，调试器是"看懂机器怎么想的，然后自己写"。

### 1.5 一条被明确推翻的设计原则

设计系统第 2 条不可动摇原则是"canvas 是主角——全屏，所有 UI 浮在它上面，永不切分它"。左右分屏的调试器**直接违反这一条**。

**决定：在 `chess/` 子项目内推翻它，并写下理由。** 代码面板不是控制器，是第二个内容视图；让它半透明浮在棋盘上会两边都读不清。

本子项目自己的规则：

> 除算法调试器（工具 ④⑤）外，canvas 仍是主角。调试器工具采用可拖拽的分栏，并保留一键折叠回全屏棋盘。

这是本子项目第二条与主仓库不同的规矩（第一条是默认语言）。独立子项目本来就该有自己的规矩，但每一条都要写下来并说明理由。

### 1.6 默认语言为英文

与仓库惯例（中文默认）相反，本子项目**英文默认、中文可切**。理由：使用者要读的是英文 A-level 课程与英文算法题，术语（fork、pin、en passant、backtracking、pruning）也都是英文。中文界面下术语仍以英文并列显示（`别子 pin`）。

#### 「双语 UI」与「双语工具」不是一回事（2026-08-07 阶段 8 定）

阶段 1–7 交付的是**双语 UI**：页签、按钮、读数、提示、图例、课文全都 `{zh, en}`。但**算法源码的注释与运行日志一直是单语中文**——`chess/core/algos/*.js` 的 `HEAD`/`BODY` 字符串数组里没有任何 `lang` 参数，`log()` 打出的也是中文（`log("第 " + (n + 1) + " 个王站在 " + best + " 号格…")`）。全部七份加起来 **867 行源码、25,727 字符，其中 7,742 个汉字**，15 处 `log`。

这是一个「工具存在的意义」级别的缺口，不是打磨项：**工具⑤ 的全部价值就是让那份算法源码可读**，而它默认英文界面、却把最该被读的那部分只用中文写。阶段 7 的最终审核在截图 `t6-unknown-7x7.png` 上直接看到这件事——整页英文 UI，两个编辑器里全是中文注释，`OUTPUT` 栏印着中文日志。

**阶段 8 的裁定：**

- **`source(opts)` 多吃一个 `lang`，且必填。** 照 `parse(source, lang)` 的先例（阶段 6 定的，理由是「默认成哪一种，都是让同一个缺陷换个地方复活」）。
- **英文以中文那一版的意思与语气为底本重写，不是逐句对译**——允许句式与举例不同，判据是「两边各自读起来都像母语者写给十六岁读者的」。
- **不变式：可执行的代码在两种语言下逐字节相同**，只有注释与 `log` 的字符串字面量不同。两道机械门守它：① 抽掉注释、把每个字符串字面量换成占位符之后两边逐字节相同；② 两种语言下解释器跑出的步数相同（注释不产生步；一次 `log` 无论字面量多长都是一步）。
- **BLANK 指令行不翻译**——它本来就同时带着 `hint` 与 `hintEn`，两种语言变体里那一行逐字相同，`parse()` 一点不用改。
- **两种语言变体的行数必须逐行对齐**：同一份源码的第 n 行，在两种语言下是同一件东西（同一行代码，或同一段注释的同一行）。因此 `blanksOf().startLine`、`Step.line`、`pristine`、`answerRange`、`judge.herSrc` **在两种语言下全部不变**。

  这条不是洁癖，是**算出来比另一条路便宜**。生成的源码是**按行索引**的：解释器每一步记 `line`，第 4 级提示靠 `pristine` 与编辑器逐行对齐划出 `answerRange`，判定靠 `judge.herSrc` 比对。行数一差，切一次语言这四样**同时**指错地方。这一页已经为它的一半付过学费——`retextNotes()` 的注释里记着：「填对了、绿色的『对了』，切一次语言就变回一句灰的『运行完成 · 144 步 · 返回值 0』，而她什么都没动」。那还只是注释行原地对换的年代；整份源码换语言，四样一起错。

  行数对齐一立，代价就全没了：**轨迹在两种语言下逐字节相同**（可执行代码本来就相同，行号又不动），所以切语言**不重跑解释器、不重建轨道**，只把编辑器里的文本换掉——比今天的 `retextNotes()` 还简单。

  写文案的代价是真实的但可付：**约束落在「段」上，不落在「句」上**。一段 6 行的中文注释要写成 6 行英文，段内句子怎么重组都行。中文一行约 27 个汉字 ≈ 54 列，英文同样信息约 72–79 列——**宽度本来就接近**，所以逐段等行数在实测里是够用的。

  **万一某一段真的写不成等行数，停下来报告，不许靠塞废话或砍内容凑数。** 阶段 8 的第一个任务就挑最小的一份（`queens.js`，81 行）先验这件事：不成立的话，在写另外 786 行之前就知道。
- **切换语言时**：编辑器里的源码若与「当前语言/参数下生成的那一份」相同（她只是在读），**静默换成新语言那一份**；若她改过，**一个字不动**并在状态栏说明——`Reset to original` 是既有退路。这条的一半地基阶段 6 已经埋了（`localStorage` 的 `src` 里存了 `lang`）。

**`minimax.js`（工具④）不在阶段 8 范围内**——改它要重做工具④ 的验收，单独成一阶段（**阶段 9a**）。

#### 9a 收口时的两点（2026-08-07 定）

- **`minimax.js` 有 0 处 `log`**（163 行生成源码、977 个汉字，全是注释）。于是「可执行代码逐字节相同」那道结构门几乎自动成立——**这反而让「英文说得对不对」成为唯一的风险面**，人工审查那两条判据在这一份上是全部。
- **工具④ 没有工具⑤ 那样的 `source()` 单一入口**：`AM.source(...)` 有**两个**调用点。阶段 8 靠 `genSource` 一处收口保证「漏传 `lang` 必然当场红字」，工具④ 没有这条通道——**9a 要补一个入口**，理由跟工具⑤ 当初一样：第三个调用点迟早会出现。
- 做完之后 `check.py` 的 `MONOLINGUAL_ALGOS` **空了**。**空白名单是个迟早会被重新打开的暗门——直接删掉这个机制**，让第八道门无条件要求所有 `algos/*.js` 双语。顺带消掉「白名单收缩只有注释、无代码强制」那条遗留。

### 2.1 单一编辑源 + 机器同步

九处 `★` 是**唯一手改的地方**。`inline_core.py` 把它们注入每个 `tools/*.html` 的标记区间：

```
/* >>> GENERATED:CHESS-CORE */ … /* <<< GENERATED:CHESS-CORE */
/* >>> GENERATED:BOARD-RENDER */ … /* <<< */
/* >>> GENERATED:VIZ-ENGINE */ … /* <<< */
/* >>> GENERATED:GAMES */ … /* <<< */      （仅回放工具）
/* >>> GENERATED:INTERP */ … /* <<< */     （仅 ④⑤）
/* >>> GENERATED:DEBUGGER */ … /* <<< */   （仅 ④⑤）
/* >>> GENERATED:ALGOS queens.js,tour-dfs.js,tour-warnsdorff.js,knight-path.js */ … /* <<< */
                                           （仅 ④⑤，算法源码以字符串内联；按页列清单）
```

这是照抄仓库现有 `scripts/sync_registry.py` 的纪律，同样接进 `.githooks/pre-commit` 与 CI。运行时每个 html 完全自足，`file://` 双击可用。

> 这看似重复，但正是本仓库的既有做法——那个 3D 引擎本身就在 61 个文件里各复制了一份。内核有单一编辑源、运行时各自独立，"单文件零依赖"没有被破坏。

`algos/*.js` 特殊：它们**不作为代码执行，而是作为字符串内联**，运行时交给 `interp.js` 解释。所以显示给使用者的源码与实际被执行的源码是同一份字符串，不可能漂移。

**`ALGOS` 标记按页列清单**（2026-08-04 定）。第一版是整目录倾倒——只有一份算法源码时无感，但工具⑤ 一落地就会让工具④ 带上四份它从不执行的算法、工具⑤ 带上 `minimax.js`。标记行自己写明这一页要哪几份：

```
/* >>> GENERATED:ALGOS queens.js,tour-dfs.js,tour-warnsdorff.js,knight-path.js */ … /* <<< GENERATED:ALGOS */
```

清单里写的是**文件名（含 `.js`）**，与 `ALGOS` 对象的键逐字相同——写成裸名再由脚本补 `.js` 是一条隐式约定，而隐式约定正是这个项目反复付过学费的东西。漏写一个键**当场报错**，而不是静默少内联一份（那会变成运行时才发现的 `ALGOS['queens.js'] === undefined`）。`check.py` 的往返校验也因此能逐页对应，而不是把所有页面对着同一份目录校验。

### 2.2 引擎裁剪

**保留**：轨道相机（球坐标 `az/el/dist` + 平移）、透视投影与近裁剪、全部绘图原语（`strokePoly` / `line3` / `glowDot` / `label3` / `drawGridXY` / `arrowAt` …）、设计令牌与配色、tab/滑杆/读数/折叠面板等 UI 组件、i18n 的 `t()` 机制、录制回放框架。

**改掉**：

| 原引擎 | 本子项目 |
|---|---|
| 连续时间积分 `theta += ω·dt` | 离散 ply 推进 |
| 共享 `samples` 环形缓冲 | **走法栈 + 局面栈**（要能撤销、要能分支）|
| 自定义存档格式 | **PGN** |

### 2.3 `chess-core.js` 接口

零依赖纯 JS，可由 `node` 直接加载（`module.exports` 与 `window` 双导出）。

```js
Position.fromFEN(fen)        // → Position
pos.toFEN()
pos.legalMoves()             // → Move[]（已过滤自杀走法）
pos.pseudoLegalMoves()       // → Move[]（未过滤，供工具 ② 的差集高亮）
pos.attacksFrom(square)      // → Square[]
pos.attackedBy(square, side) // → Square[]
pos.make(move)               // → 新 Position（不可变）
pos.inCheck(side)            // → bool
pos.status()                 // 'ongoing'|'check'|'checkmate'|'stalemate'
                             // |'insufficient'|'fifty'|'repetition'
Move.toSAN(pos)  Move.toUCI()
parseSAN(pos, s) parseUCI(pos, s)
parsePGN(text)               // → { headers, moves[], result }
writePGN(headers, moves)
perft(pos, depth)            // → number（测试用）
```

内部表示采用 **0x88**（越界检测是一次按位与，走法生成简洁且不易错）。`Position` 不可变，`make()` 返回新对象——这让工具 ④⑤ 的树搜索和回溯天然安全，不需要 unmake。

### 2.4 `board-render.js` 接口（参数化棋盘）

算法工具与前四个工具**共用同一套棋盘和同一套棋子**——八皇后摆的是真正的后，骑士巡游走的是真正的马。

```js
drawBoard(C, { files: 8, ranks: 8, origin, cell, coords: true, mask: null })
drawPiece(C, { piece, square, scale, alpha, facing })
```

- 默认 `8×8`；N 皇后 `files=ranks=N`，**N ∈ [4, 8]**；骑士巡游 **`3×4` / `4×5` / `3×7`**（**非方形**）；博弈树用 `4×4` 简化盘
  - 两处范围都是 §4⑤ 实测收窄的：N=9 与巡游的 5×5 以上在 `STEP_LIMIT` 下跑不完。**巡游的盘不再是方形**，所以 `files !== ranks` 是常态而不是边角情况——坐标标注与取景都要按这个测
- 坐标标注随尺寸自适应（`a`–`h` 自动扩到 `a`–`l`）
- `mask` 预留给"带禁区的棋盘"这类变体题

### 2.5 棋子渲染：SVG 路径 → `Path2D` → Canvas

棋子用 **SVG 的 `d` 路径数据**书写（可在矢量工具里画，也可手写），运行时 `new Path2D(d)` 交给 Canvas 2D 绘制。既保留 SVG 的作者体验，又不引入任何外部文件或加载器。

现阶段每颗子画成**朝向相机的剪影** + 脚下一枚随棋盘做透视变换的圆盘。白方浅描边、黑方暗描边，任意视角都读得清，贴合示波器美学。

**关于将来上 3D 的诚实评估**（现在只留接缝，不留承诺）：

- WebGL + `.glb` 最"正统"，但同时打破两条底线——零依赖（要模型加载器）和 Canvas-2D 引擎（整套投影/绘图原语要重写）。不是小升级。
- 更现实的中间路：棋子除马以外全是**旋转体**，可把同一份 SVG 侧影绕竖轴车削（lathe）成低模，仍用 Canvas 2D 画。马需单独处理。
- 性能须老实算：32 子 × 12 边 × 10 段 ≈ 3800 面，Canvas 2D 路径填充在这个量级会掉到 30fps 以下。因此它更可能是"静态视角下的展示模式"，而非可边转相机边跑的常态。

**决定**：渲染器抽成可替换接口 `drawPiece(...)`，从第一天起记录性能预算 **32 子的单帧绘制耗时 ≤4ms（`getImageData` 强制光栅化后测量）**。是否升级、升到哪一档，等有真实数据再定。（性能预算最初写成"32 子 @ 60fps"，实测才发现这个判据量的是宿主刷新率而非绘制代码本身——30Hz 宿主上无论代码多快都过不了，144Hz 宿主上无论代码多慢都轻松过；改成绘制耗时后，判据才真正只随代码改变。）

### 2.6 `interp.js` — 可单步的 JavaScript 子集解释器

工具 ④⑤ 的核心。约 700–900 行，零依赖，可由 `node` 直接加载与测试。

**为什么自己写解释器，而不是用生成器打点**：使用者的最终目标是**学会设计算法**。生成器打点方案里，调用栈只能手工维护、没有真正的"步入"、而且她无法改代码重跑——都会在"我想自己写一个"那一刻卡住。解释器把这三样一次解决，并且屏幕上显示的是**她能直接复制进 `node` 跑的真 JS**，不是伪代码。

**支持的子集**：`let` / `const`、赋值、数字/字符串/布尔/`null`、数组字面量与索引、对象字面量与属性访问、一元与二元运算、逻辑运算与短路、`if/else`、`for`、`for…of`、`while`、`break`/`continue`、函数声明与调用、`return`、**递归**、箭头函数、模板字符串。**阶段 9b 起另加**：BigInt（`123n` 字面量与 `BigInt(x)` 内建）与 `& | ^ ~ << >>` 六个位运算符（`>>>` 不加，见 §7.7）。

**明确不支持**：`class`、`async`/`await`、`try/catch`、正则、`this`、原型链、解构、展开运算符。遇到不支持的语法在解析阶段就报明确的错（`Unsupported syntax: class declaration at line 12`），而不是运行到一半崩。

**实现方式**：解释器本身**用 JS 生成器写**（`function* evalNode(node)` + `yield*` 递归下降），每到一个语句边界 `yield` 一次。这样递归下降的写法天然可以在任意点暂停，代码量比手写显式栈机小得多，且不易错。

**宿主桥接**：算法通过一组内置函数驱动可视化——`mark(square, kind)`、`place(square, piece)`、`clear(square)`、`log(msg)`、`attacked(square)`。**这是算法与棋盘之间唯一的接口**，算法源码里看得见它们，所以使用者能明白"这一行为什么让那一格变了色"。

**快照策略**：每步记录**增量**而非全量（`{ line, frameOp, varDelta, boardOps, out }`），回放时正放前进、反放撤销。默认轨迹上限 **50,000 步**；超限则停止记录，并在读数区显式写明"已达上限，省略 N 步"——不静默截断。

### 2.7 `debugger.js` — ④⑤ 共用的调试器面板

| 区 | 内容 |
|---|---|
| 代码 | 当前行高亮；已执行过的行留淡色痕迹；点行号设断点 |
| 调用栈 | 帧列表，可点击跳到该帧。**栈深度就是该工具的 z 轴** |
| 变量 | 当前作用域的变量与值；本步变化的值闪一下 |
| 输出 | 每步一行日志（`try (3,5) → attacked by queen at (1,3)`）|
| 读数 | 尝试 / 回溯 / 剪枝次数、已用步数，与理论复杂度并列显示 |

**控制条**：`播放 / 暂停 / 单步 / 后退 / 步入 / 步过 / 步出 / 跑到断点 / 速度`。

"后退"能做到，是因为采用**先跑完、记全轨迹、再回放**的策略——单步、后退、拖时间轴、跳到任意步全部免费。这也正是设计系统 §11「存轨迹不存种子」在这里的应用。

**棋盘侧四种状态**各占一色（沿用 rose → violet → emerald → orange 顺序）：正在尝试 / 已确认 / 被剪枝 / 回溯撤销。

### 2.8 `editor.js` — 内嵌代码编辑器

代码面板**可编辑**。她能改算法、当场重跑、看棋盘上的结果如何变化。这是"学会设计算法"这个最终目的的落点：把 Warnsdorff 的启发式函数改成随便一个别的规则，巡游立刻失败——这一课比任何讲解都直接。

**零依赖下怎么做语法高亮**（不能用 CodeMirror / Monaco）：

采用**透明 `<textarea>` 叠在高亮层上**的经典做法——`<textarea>` 文字透明但光标可见，负责全部输入、选区、原生撤销、IME；底下一层 `<pre>` 渲染着色后的 token；两者字体度量完全一致、滚动同步。约 80 行，行为比自己实现 `contenteditable` 稳得多。

**高亮几乎不花额外成本**：`interp.js` 本来就需要词法分析器，编辑器**直接复用它**。因此高亮看到的 token 流与执行看到的是同一份——不存在"高亮说这是关键字、解释器说不是"的分歧。

**实时语法检查**：输入防抖后交给 `interp.js` 的解析器：

- 错误处波浪下划线，行号槽内红点，悬停显示消息
- 不支持的语法在此明确报出：`Unsupported syntax: class declaration (line 12). This interpreter supports a subset of JavaScript.`
- 有语法错时 `Run` 按钮禁用，不会跑到一半才崩

**其余编辑器行为**：行号槽（**断点也点在这里**）、当前执行行高亮（与调试器共用同一状态）、Tab 缩进、括号配对高亮。

**编辑后的流程**：改动 → 语法通过 → `Run` 亮起 → 重新解释执行、生成新轨迹 → 棋盘与调试器重置到第 0 步。

**安全与保护**：解释器天然是沙箱（子集里没有网络、没有文件系统、没有 `eval`）。真正需要防的是死循环——已有的 50,000 步轨迹上限同时充当执行上限，超限则停止并明确提示，而不是卡死页面。

**持久化**：改过的版本存 `localStorage`（按题目键），并提供 `Reset to original`。另提供 `Export .js`——导出的文件她可以直接在 `node` 里跑，因为那本来就是真 JS。

### 2.9 `exercise.js` — 挖空练习与差分定位

这是"最终目的"的落点。前面所有工具都是**看**，这是第一次**做**。

#### 挖空怎么声明

直接写在 `algos/*.js` 里，用注释指令圈出（**下面这个形状是 2026-08-05 落地后回写的，五个属性一个都不能少**）：

```js
// >>> BLANK id=safe-return level=1 fill="return false;" hint="三条线都空着才算安全…" hintEn="A square is safe only when all three lines are clear…"
return !cols[c] && !diagDown[r + c] && !diagUp[r - c + N];
// <<< BLANK
```

`id=` / `level=` 是裸值（读到下一个空白为止），`fill=` / `hint=` / `hintEn=` 是双引号串；属性顺序不作要求。规格原文只有 `level=` 与 `hint=`，另外三个是落地时长出来的，各有各的硬理由：

- **`id=`** —— `localStorage` 的键必须稳定（§2.9 末尾那条 `chess.exercise.v1.<problem>.<blank>`）。按序号做键的话，将来在前面加一个空就会把她所有的答案错位一格。它同时还是 UI 的锚点：一道题可以有两个空，占位注释行不带 id 就**逐字节相同**，而切语言的原地对换与第 4 级「填进去」的定位都靠这一行认路 —— 两行一样，两个空就会互相顶掉。提示面板每一行也按 id 标题，屏幕上下两处对得上。
- **`fill=`** —— 挖掉一段之后**源码还得能跑**。§2.9 第 3 条说「Run 只跑，判定归 Check」，那么她一个字没填就按 Run 也不许报错，否则「先看懂自己写的东西干了什么」根本无从开始。`fill` 就是那个占位实现：能跑完、但十有八九答错。它必须逐题挑 —— 阶段 6 实测过一次教训：`queens` 的 `safe-return` 原本给的是 `return true;`（恒真），等于把剪枝整个拿掉，搜索树退化成满的 `N^N`，N≥6 当场撞上 `STEP_LIMIT` 被截断，「占位版必须仍然能跑」自己就不成立了。
- **`hintEn=`** —— 这套工具默认 EN（§1.6）。只有中文 `hint` 的话，默认语言下提示是空的。

**参考答案就是那份正在运行的源码本身**，不是另写一份。练习模式下这一段被替换成占位符与提示；正常模式下它就是被执行的代码。**因此两者不可能漂移**——这与 §2.1 里算法源码"显示与执行同一份字符串"是同一条纪律。

#### `parse()` 交三样东西，不是两样

```
parse(source, lang) → { blanks, placeholder, clean }
```

| 产出 | 是什么 |
|---|---|
| `blanks` | 挖空清单（`id` / `level` / `body` / `fill` / `hint` / `indent`） |
| `placeholder` | **练习模式**的源码：每个挖空体换成「占位注释 + `fill`」 |
| `clean` | **正常模式**的源码：只剥掉那两行 `// >>> BLANK` / `// <<< BLANK` 指令，挖空体原样保留 |

`clean` 是落地时补的第三份产出，它不是锦上添花。`algos/*.js` 的 `source()` 吐出来的原文里就嵌着指令行，而工具⑤ 正常模式是把那份原文直接喂给编辑器的 —— 不剥的话，今天打开 `queens`，`function safe` 里就摆着两行五百来字符的 `// >>> BLANK id=… fill="…" hint="…" hintEn="…"`：那是给解析器看的元数据，不是给人读的代码，而且 `fill=` 与 `hint=` 把答案和提示一起写在了她眼前 —— 正常模式下这一题就没了。剥这件事必须走 `parse()`，**不许让页面自己写一条正则**：同一段「什么算指令行」的知识分成两份，迟早分岔。

`lang` 是**必填**参数（占位注释那一行的语言），没有默认值：默认成 `zh` 会让「英文是默认语言」这个缺陷换个地方原样复活，默认成 `en` 又会让中文使用者的提示悄悄消失。要哪种语言，调用方自己说。切语言时 UI **不重新生成占位源码、更不重跑解释器**，而是拿 `noteLine(b,'zh')` 与 `noteLine(b,'en')` 两份文本在编辑器现有内容里逐行对换 —— 她自己改过的行对不上任何一份，原样留着，切语言不会吃掉她写了一半的答案。

三级难度：`level=1` 填一个表达式（条件、返回值）；`level=2` 填一整个语句块；`level=3` 填一整个函数（给签名与注释）。

#### 怎么判对：比行为，不比文本

**绝不比对源码文本**——同一个条件有无数种正确写法。

判定方式是**跑她的版本和参考版本，比对可观测行为**。这几乎不花额外成本，因为解释器本来就要跑，而且轨迹本来就要记。

比什么由每道题自己声明，避免"正确但写法不同"被误判：

```js
check: { result: true, boardOps: true, counters: ['solutions'] }
```

例如 N 皇后里，一个不同写法但正确的 `isSafe` 会给出完全相同的解序列，所以 `boardOps` 可比；但若挖的是剪枝顺序相关的部分，就只比 `result` 与解数，不比步序。**这一条必须逐题显式声明，不能有默认值**——默认值会悄悄地把正确答案判错。

#### 判错时给什么：定位到第一处分歧

"错了"是没用的反馈。因为两个版本的完整轨迹都在手上，可以做到更好的事：

> **找出她的版本与参考版本行为分歧的第一步，把调试器直接跳到那一步，两边并排显示。**

她看到的是"跑到第 47 步为止你和参考完全一致，第 48 步参考认为 (3,5) 安全、你的版本认为不安全"——而不是一个红叉。这是这个功能真正的价值，也是它值得单独成一个模块的原因。

#### 提示分级，且随时可以放弃

提示逐级给，不一次给完：文字提示 → 点明涉及了哪几个变量 → 参考答案的结构骨架（保留控制流、挖掉表达式）→ 完整答案。

**任何时候都可以直接看答案并继续。** 这是自学工具，不是考试；卡住而无法前进只会让她关掉页面。

#### 持久化

每个 `(题目, 挖空)` 的作答存 `localStorage`，含尝试次数与用了第几级提示——这样以后想加"哪些概念她反复卡住"的回顾视图，数据已经在了。

键 `chess.exercise.v1.<problem>.<blank>`，值 `{ text, attempts, hintLevel, solvedAt }`。只在练习模式下写，正常模式一个字节都不碰。schema 变了就换版本前缀、不做迁移。§9 已明确：不做计分、评级、进度条、成就。

#### 阶段 6 开工前定下的四条（2026-08-04）

这四条是 §2.9 落地时才浮出来的，规格原文没有：

1. **`tourKnight` 进练习模式时降为「参考 vs 她」，DFS 那份不跑、只以只读文本留在旁边当对照。** 它的两条轨道在正常模式下装的是「DFS vs Warnsdorff」，而练习需要「参考 vs 她」——两组对比争同一块屏幕。降级的好处不只是省屏幕和帧预算：挖空点本来就是 Warnsdorff 比 DFS 多出来的那一段，所以那份只读对照**本身就是提示**（「你要填的就是它比左边多出来的那件事」）。练习 UI 因此三题同形，只有一种形状——阶段 5 的教训是多一种形状就多一类只在那种形状下发作的 bug。

2. **整份源码照旧可编辑**，挖空区只是被替换成占位行。判定本来就只看行为不看文本，所以她在别处改坏了什么自然会被覆盖到——而且分歧定位会直接指到她改坏的那一步。`editor.js` 因此一行不改（它是工具 ④⑤ 共用的核心模块，动它要重做工具 ④ 的验收）。

3. **Run 只跑，判定归 Check。** Run 照旧：跑她的版本、上棋盘、可单步——她能先自己看懂自己写的东西干了什么。按 Check 才跟参考版本对行为、才跳到分歧步。若 Run 就判定，她每次迭代都会被强行拽走游标，而「先看懂自己的错版本在干嘛」本身就是调试能力。

4. **练习模式下两条轨道各自定位，不共用游标。** 这是练习模式与并排模式在语义上唯一的分叉：同一件事她的版本可能发生在第 60 步、参考在第 48 步。阶段 5 的 `syncTracks` 是「一个游标同时推两条」，练习模式必须绕开它。这是最容易写出「看起来对但游标错位」的地方。

#### 首批挖空选点（阶段 6）

**五个挖空**（`queens` 两个、`knightPath` 两个、`tourKnight` 一个），三个难度级都覆盖：

| 题 | `id` | 挖空 | 级 | 等价改写（§7.4 的筛子） |
|---|---|---|---|---|
| `queens` | `safe-return` | `safe()` 的返回式 | 1 | 拆成三条 `if (…) return false` 再 `return true` |
| `queens` | `undo` | 回溯撤销那三行 | 2 | 三条赋值换顺序 |
| `knightPath` | `on-board` | `onBoard()` 的返回式 | 1 | `return !(x < 0 \|\| x >= W \|\| y < 0 \|\| y >= W)` |
| `knightPath` | `seen-test` | `if (dist[nb] >= 0)`——这一格碰过没有 | 1 | `dist[nb] !== -1` |
| `tourKnight` | `degree-fn` | 整个 `degree()` 函数（给签名与注释）| 3 | 循环写法自由 |

**`tourKnight` 只有这一个空 —— 原表里那一行「`degree()` 里的计数行 / 1 级」在落地时删掉了**（2026-08-05，交付时裁定）。原因是那两个空**互相嵌套**：3 级那个空的挖空体就是整个 `degree()` 函数，把 1 级那个计数行整个包在里面，于是源码里会写出 `>>> BLANK` 套 `>>> BLANK` —— 而 `parse()` 见到嵌套**当场抛**。这一条是硬的，不是实现偷懒：允许嵌套就得回答「外层的 `fill=` 里那个内层空算谁的、她填外层时内层的存档怎么办」，而这两个问题都没有不含糊的答案。

留下的是 3 级那个：**`degree-fn` 是整个阶段唯一的 3 级挖空**，丢掉它三个难度级就不齐了；1 级的空另外还有三个（`safe-return`、`on-board`、`seen-test`），少一个不伤。这张表真正要保证的是「三个难度级都覆盖」，那一条仍然成立。

**Warnsdorff 那段手写选择排序故意不挖**，尽管它看起来是最诱人的挖空点（两份源码唯一实质不同的地方）。理由正是筛子本身：换成插入排序是货真价实的「正确但写法不同」，可两者**在候选出路数并列时的打破方式不一样**，于是走出另一条同样合法的巡游、`boardOps` 全不一样，会被判错。这是 §7.4 说的「判定过严」的教科书案例。要挖它，得先在「`check` 只比 `result`（那这道挖空基本没有判定力）」与「提示里规定并列取先出现者（那等于把答案写进提示）」之间选一个——**留到她实际用过一轮之后再定**，§8 本来就说这一阶段的产出质量要在使用之后复盘。

另外两条边界：**任一边撞 `STEP_LIMIT` 且分歧没在截断之前出现，就不给判决**——读数显示「跑不完，判不了」，不是「错」（`null` 表示「不知道」，永远不许变成布尔值）。**Check 要跑两遍**（参考 + 她，queens N=8 是 15.7 万步 ×2），必须放进 `withBusy`，不能同步跑在绘制路径里。

## 3. 标准术语规范

### 3.1 记谱

- **默认 SAN**：`Nf3` `O-O` `O-O-O` `exd5` `e8=Q+` `Rxd4#` `1-0` `0-1` `1/2-1/2`
- **提供 SAN ⇄ UCI 切换**：`e2e4` `e7e8q`。这条专为使用者准备——棋类算法题与所有引擎接口说 UCI，棋书与棋谱说 SAN，两边都得认得。
- 消歧规则完整实现（`Nbd2`、`R1e2`、`Qh4e1`）

## 4. 五个工具

配色沿用设计系统：一条曲线一个颜色，按 rose → violet → emerald → orange 固定顺序，同一颜色在六处复用（图例点、曲线体、投影虚线、头部辉光点、读数粗体值、公式标签）。每个工具第一个视角必须是 `iso`（双击回家），并有一个正交的"顿悟视角"。

### ① `chess-moves-geometry` — Geometry of Movement

**顿悟**：每个棋子就是一组向量规则；而"控制中心"是可以量出来的数，不是口号。

| tab | 内容 |
|---|---|
| `piece` | 选棋种、点格子放子，实时高亮攻击域。这是学走法的地方 |
| `field` | **最少步数场**（z = 步数）。马的场最反直觉，且**不是平移不变的**：正相邻（同行或同列）全盘恒为 3 步；对角相邻只取 2 或 4 —— 中心是 2 步，角上却要 4 步（a1→b2）。无限棋盘上马的距离场平移不变，是 8×8 的边界把它掰断了 |
| `mobility` | 机动性高度场：每种棋子在 64 格各自能攻击几格。骑士中心 8 格、角上 2 格 |
| `metric` | 距离度量：王 = 切比雪夫距离 L∞、车 = 两步内可达全盘。A-level 范数的具象版 |

**顿悟视角**：`field` tab 的正交俯视 + 侧视对照——俯视看覆盖形状，侧视看阶梯高度。

### ② `chess-rules-check-mate` — Rules, Legality and Mate

**顿悟**：合法走法 = 伪合法 ∩ 不自杀。将死不是一种特殊状态，是"合法走法集合为空且正被将军"。

| tab | 内容 |
|---|---|
| `legal` | 伪合法 vs 合法**同屏双色高亮**，差集正好是被别住的子（pin）。整个工具最关键的一页 |
| `special` | 易位（四个前提逐条亮灯）、吃过路兵（含"只在下一步有效"的时间窗）、升变（含 underpromotion）|
| `check` | z = ply：展开对手所有应手，全部落空 = checkmate；无合法走法但未被将军 = stalemate |
| `mate` | 基本杀法 K+Q vs K、K+R vs K。学会走棋后第一件真正能做到的事 |

易位的四个前提在 `special` tab 逐条以指示灯呈现：王未动过、该车未动过、之间无子、王的起点/路径/终点均不受攻击。

### ③ `chess-game-replay` — Reading a Game

**顿悟**：一局棋是三维里的一条曲线。

| tab | 内容 |
|---|---|
| `board` | 播放条 + SAN 步表，历史局面沿 z 堆叠 |
| `trace` | **子力轨迹**：每颗子沿 z 的三维折线。一眼看出"这只马走了 9 步，那只象一步没动" |
| `eval` | 沿回合的三条曲线：子力差（rose）/ 控制格数（violet）/ 王的安全度（emerald）|
| `heat` | 整局累计热力：哪些格是战场，哪些从头到尾没人碰 |

**输入**：30 局预置（内联，保证 `file://` 可用）+ PGN 文件拖入 + FEN 粘贴。

**王的安全度**定义（须明确，否则实现会各写各的）：己方王周围 8 格中被对方攻击的格数，取负值；范围 [-8, 0]。这是一个粗糙但可解释的指标，工具内会说明它粗糙在哪。

### ④ `chess-search-minimax` — Game Trees and Search

**顿悟**：α-β 剪掉的体积是肉眼可见的一块；而香农数说明为什么永远剪不完。

**采用分屏调试器布局**（见 §1.5、§2.7）：左边是 minimax / α-β 的真实源码在单步跑，右边是博弈树。走到 `if (beta <= alpha) break;` 那一行时，树上整片枝子同时塌掉。

| tab | 内容 |
|---|---|
| `tree` | 纯 minimax，z = 搜索深度，值逐层回传。调试器的调用栈就是树上的当前路径 |
| `prune` | 同一棵树开 α-β：被剪的枝染灰塌陷，读数 `访问节点 12,438 → 1,207` |
| `order` | 走法排序的威力：随机序 vs 吃子优先序，剪枝率差数倍——**O(b^d) 与 O(b^(d/2)) 的实物证明** |
| `shannon` | 分支因子 35 的指数爆炸 vs 可观测宇宙原子数（此 tab 无调试器，是纯图表）|

**用简化棋盘**：树画得下的前提是局面要小。采用 `4×4` 简化盘与若干残局局面，而非开局全盘。这一点已与使用者确认。

评估函数保持**可解释的简单**：子力值 + 中心控制，两项，都能在读数区看到分解。目的不是下得好，是让人看懂搜索。

#### 实测参数（阶段 4 设计时量出来的，不是估的）

起始局面 **`K.N. / .PP. / ..pp / .n.k`**（白 K+N+2P vs 黑 k+n+2p）。它是**测着挑的**：要让「纯 minimax 撞墙」明确无歧义，同时 α-β 在同一格留有余量。

| 深度 | 纯 minimax | α-β | 吃子优先序 | 极小极大值 |
|---|---|---|---|---|
| 1 | 1,473（1%） | 1,492（1%） | 1,544（1%） | 124 |
| 2 | 9,482（5%） | 6,896（3%） | 5,631（3%） | 0 |
| 3 | 62,143（31%） | 37,791（19%） | 28,790（14%） | 136 |
| 4 | **200,000 截断 ✗** | 123,499（62%） | 70,575（35%） | −12 |

（这组数字由 `chess/core/algos/minimax.js` 实测复现，随该文件一起维护：生成的源码哪怕只多一条顶层声明，整列都会平移几步，两边必须一起改。）

**第 4 层就是这一课**：同一个设置下纯 minimax 根本跑不完（`truncated`，返回 `undefined`），α-β 从容跑完。这比任何倍数都硬——不剪枝不是「慢一点」，是**做不到**。这正是约束 4 说的「把撞上上限呈现成这一课的内容，而不是让人以为工具坏了」。

**深度滑杆：范围 1–4，默认停在 2，深度 1 处配一句说明「这一层没有东西可剪」**（Task 8）。深度 1 是个真实的反例——这一层所有子节点都是叶子，剪枝那两行只增加执行步数、一次也切不掉分支，于是 α-β 比纯 minimax **多** 19 步（1,492 vs 1,473）、吃子优先序多 71 步。**不要把这一格从滑杆上拿掉**：它是唯一能证明「剪枝不是魔法」的一行，自己滑到深度 1、发现剪枝反而更慢、再想明白为什么的人，学到的比记住标题多。默认值避开它就够了，藏起来是另一回事。

**关键不变量（阶段 4 的对拍测试）**：α-β 与纯 minimax 必须返回**同一个值**——同一棵树、同一个极小极大值。上表四个深度、三种模式已全部验证一致（124 / 0 / 136 / −12）。剪枝只允许省掉搜索，不允许改变答案。

**性能上的巧合要留意**：深度 4 的 `tree` tab 轨迹是**被截断的**，而截断轨迹正是 `debugger.js` 里 `matchFrames` 的最坏情形（帧永不关闭 → 早退分支失效 → 每次推导 O(trace.length)）。**撞墙演示恰好就是性能最坏点**，增量树模型必须在这一格上撑住。

#### 算法源码的子集约束（实测得出）

`algos/*.js` 交给 `interp.js` 解释执行，写它们时受子集限制，这几条是实施前量出来的：

- **没有三元运算符**（`a ? b : c` 报 `unsupported`）——用 `if/else` 展开。
- **宿主桥接是写死的五个名字**（`log` / `mark` / `place` / `clear` / `attacked`），不可扩展。工具④ 一个都不用：树完全从**调用栈**推导（`callStack` / `frameIds` / `locals(cur, depth)`），`search()` 的每一帧就是树上的一个节点。这也正是 §1.4「z 轴就是调用栈的深度」的直接兑现。
- **走法生成与评估也必须写在子集里**，因此每节点成本比"宿主提供走法"高约十倍。
- **`applyMove` 推荐用 make/unmake**（就地改再改回）而不是整盘拷贝，**隔离实测约贵 21%**：α-β 深度 4 整盘拷贝 149,178 步、make/unmake 123,499 步，**两者都没越过 200,000**（其余两个模式同量级：plain +23%、吃子优先序 +18%，三者返回值均不变）。
  - ⚠️ **更正**：本节早先写的「差一整层深度：整盘拷贝需 245,847 步（超限）」**是错的**。那个数字来自一份同时还缺走法编码（`from*16+to`）和预计算偏移表的旧实现，把三处改动的收益一并算到了 make/unmake 头上——一次无法隔离所测变量的测量，正是本仓库已经吃过三次亏的失败模式。make/unmake 仍是推荐写法，理由是它确实更便宜，**不是**因为没它就跑不完。
  - **不要为这条写步数回归断言**。20% 且不跨任何阈值，而 `algos/*.js` 本来就是拿给使用者改的文件（§2.8），这种断言只会在每一次正当改动上误伤。
- **棋子编号表与分值表必须用同一套具名常量索引**。工具④ 的第一版栽在这里：分值表照 `chess-core.js` 的 `P=1 N=2 B=3 R=4 Q=5 K=6` 写，而 4×4 玩具用的是 `1=P 2=N 4=R 5=K`，于是 `VAL[5]`（王）静默变成 **0 分**、`10000` 落在谁也够不到的下标 6 上。后果不是慢，是**教错**：搜索认为送掉自己的王是免费的，而使用者会看着它得出「minimax 就是这样」的结论。修正后深度 3 的极小极大值从 112 变成 136（深度 2/4 的答案、撞墙格局、三模式一致性均不受影响）。写 `VAL[KING] = 10000;`，不写裸下标。

### ⑤ `chess-board-algorithms` — Classic Problems on the Board

**顿悟**：同一块棋盘，是全部经典算法范式的共同舞台；而算法不是魔法，是一行一行跑出来的。

同样采用分屏调试器布局。棋盘尺寸随题目而变（§2.4），棋子用的是真棋子——八皇后摆的是真正的后，骑士巡游走的是真正的马。

**阶段 5 交三题（三个范式）**，其余两题与 §2.9 挖空各自成阶段（2026-08-04 定）。阶段 5 已于 2026-08-04 交付（PR #91），下表的「阶段」列即最终归属：

| 键 | 题目 | 范式 | z 轴 | 可调 | 阶段 |
|---|---|---|---|---|---|
| `queens` | N 皇后 | 回溯 + 剪枝 | 递归深度——栈长出又缩回 | **N ∈ [4,8]**；解数 2/10/4/40/92 | 5 ✔ |
| `tourKnight` | 骑士巡游 · 朴素 DFS **与** Warnsdorff | 回溯 vs 贪心启发式 | 递归深度 / 步序 1→N² | 盘面 **3×4 / 3×5 / 4×5 / 3×7**，角起 | 5 ✔ |
| `knightPath` | 马的最短路 | BFS | BFS 层数 | 目标格（起点固定 a1） | 5 ✔ |
| `rookCover` | **带障碍盘**上①最多能摆几辆互相吃不到的车 ②盖住每个空格最少要点亮几条线（段） | 二分图匹配 + König 定理 | `walk` 递归深度（「请人挪窝」传了几手） | 盘面（四档手挑） | 7 ✔ |

**这两题的题面在 2026-08-05 阶段 7 设计时改过，原因是原题面无法成立**（实测，不是推断）：

- **`rookCover` 原写「最少 8 车覆盖全盘」——空盘上这是个假题。** 8×8 空盘的答案恒为 8（每行一个，摆哪都行），二分图匹配与 König 定理**根本用不上**。模型有戏的前提是盘上有障碍：车被障碍挡住，一行断成若干**行段**、一列断成若干**列段**，一个空格同时属于一个行段与一个列段——**那才是二分图的边**，最小覆盖才不等于行数。
- **⚠ 2026-08-06 二次订正：「最大匹配 = 最少的车数」也不成立，题面第二次改。** 上一条把题面改成了「带障碍盘上用**最少的车**覆盖所有空格」，那句仍然是错的（阶段 7 Task 2 的执行者发现、审查独立验证）：**一辆车是二分图里的一条边**，它一次占住一个行段**和**一个列段，所以 k 辆车能点亮的点数最多是 2k；König 给的是「最少的**线**」，不是「最少的**车**」。最小反例只有 2×2（挖掉一格：最大匹配 2，一辆车就盖满剩下三格）；60 块随机小盘里 **49 块的最少车数严格更小、反向一次都没有**；本工具四档盘上「最大匹配 / 最少车数」分别是 **5/5、7/4、7/5、9/5**。带障碍的车支配问题本身是另一路难题，不是匹配能解的。**现在的题面是两个都恰好等于最大匹配的问法**：①最多能摆几辆互相吃不到的车 ②盖住每个空格最少要点亮几条**线（段）**。「算完之后这些车顺手也盖住了所有空格」是真的、也验过，但**必须括注「≠ 最少」**。四处文案（`core/algos/rook-cover.js` 的 HEAD、页面 `PROBLEMS.rookCover`、阶段 7 计划的 Task 2 题面段、本表）已同时改。
- **「可调：棋种」这一栏删掉。** 后能走斜线，二分图模型当场失效；这道题只能是车。
- **`kingDominate` 原写「贪心 vs 精确，差距可见」——在矩形空盘上差距不存在。** 实测 4×4 / 5×5 / 5×6 / 6×6 / 6×7 / 7×7 / 7×8 / 8×8 八种盘，**贪心与精确的答案完全相同**（8×8 都是 9）。矩形盘上王的结构太规整，贪心自然挑中 3×3 块的中心，那恰好就是最优解。**加障碍之后差距才出现**：6×6 随机布障碍，25 盘里有 15–18 盘贪心不是最优。

| 7×7 三障碍 | 2,512 | **7,180,601** |
| 8×8 空盘 | 4,356 | **72,560,984** |

**7×7 上精确解跳了三个数量级，8×8 是 7.26 千万次操作——所以 8×8 的精确支配集根本不可能进这个工具。** 这不是坏消息，是这一题的落点：前面五个工具都在讲「算法怎么跑」，最后一档讲的是**为什么现实里要用贪心**——不是因为它更好，是因为最优解你等不起，而这件事在屏幕上可以亲眼看见。

**7×7 那一档必须显示「跑不完，判不了」，不许显示「8 是最优」**——贪心给出 8，而工具**没有证明** 8 是最优（`null` 表示「不知道」永不变成数字，§2.9 的 `unknown` 通道正是为这类情形建的）。

**`kingDominate` 是同屏并排的第二个键**（`sources: ['king-greedy.js', 'king-exact.js']`），与 `tourKnight` 同形——「贪心 vs 精确」这句话字面上就要求两份源码同时在屏幕上。

**盘面是四档不是三档**（2026-08-04 阶段 5 定）。第四档 3×5 是交付时加的：3×4 上两个算法**都零回溯**，于是 §2.7 的 `back` 状态与深度压暗在那一档上永远不出现——只有三档的话，这个页面最精致的那段显示逻辑没有任何一档能展示它。3×5 另有一件别处没有的事，见下面的实测表。

**两种巡游是同一个键 `tourKnight`，同屏并排**——同一个问题、同一块盘、两份可以逐行对比的源码。这是「算法设计」这件事本身最直观的一课，所以它们必须同时在屏幕上，而不是两个要来回切的 tab。

**它仍然是两份 `algos/*.js`**（`tour-dfs.js` 与 `tour-warnsdorff.js`），因为要对比的正是两份源码本身；一个键持有两份源码，是 `PROBLEMS` 里唯一这样的条目。所以那条「一题 = 一个键 + 一个文件」的口径对它要写成 `sources: ['tour-dfs.js', 'tour-warnsdorff.js']`——**架构要能表达这件事，而不是逼它拆成两个键**，否则同屏对比就散了。

#### 四道题的裁定（2026-08-07 阶段 9 定）

把这四道的范式栏跟已交付的五题摆在一起看，**有两道是重范式的**：`independent` 的范式栏跟 `queens` 逐字相同（回溯 + 剪枝），`fieldBFS` 与 `knightPath` 都是 BFS。阶段 5 定的原则是「三个**互不重复的范式**」，所以这两道要么换个理由存在，要么不该收。**裁定是收，但存在的理由必须改成「教迁移」，并且写进它们的 tips。** 多一道同范式的题不教新技术——它教的是**同一把锤子敲不同的钉子**，而那本身值得教。既然如此，两道题都得让「敲出来的钉子确实不一样」这件事看得见：

- **`independent` 必须用马，不许用后。** 后的最大独立集**恰好就是 N 皇后**——用后的话这道题跟 `queens` 一字不差，白加。马在 8×8 上答案是 **32**（马永远落到异色格，所以同色的 32 格互不攻击），而 `queens` 的答案恰好是 N。**两个答案的形状完全不同**，这个对照才是它存在的理由。
- **`fieldBFS` 与 `knightPath` 的差别只有一行**（队列初始塞 N 个起点而不是 1 个），而那正是要教的：**迁移的代价是一行**。tips 必须明说这件事，否则它只是又一道 BFS。

**`bitboard` 的「64 位」在这个解释器上做不到，要先扩解释器（9b）。** `interp.js` **故意**不支持位运算——`& | ^ ~ << >>` 六个记号都在词法表里，存在的意义正是认出来然后友好地拒绝（`UNSUPPORTED_BINOP`，复审 I4 定的子集边界），`interp.test.js` 另有 6 条测试断言它们被拒绝。而且**就算加了运算符也不够**：JS 的位运算是 32 位的（`1 << 32 === 1`），一块 64 格的棋盘放不进一个 JS 数。实测：4×4 = 16 位、5×5 = 25 位装得下，6×6 = 36 位、8×8 = 64 位溢出。**所以 8×8 真位盘要 BigInt**，那是 9b 的内容。

**`pathCount` 与 `fieldBFS` 共同要求「每格带一个标量」**（路径数 / 最少步数），而工具⑤ 今天只能给格子四种 mark 状态（`try`/`ok`/`cut`/`back`）。这会**再次撞破「加一题只许动三处」**——跟阶段 7 的 `blocked`（墙画不出来）是同一类缺口。处理方式照阶段 7：**扩既有返回值、零新钩子优先**，并且**只设计一次**（先做的那道题付账，见 §8）。两者的呈现还不一样：`pathCount` 的数会组合爆炸（8×8 上帕斯卡三角到几千），立成高度动态范围没法看，要**写数字**；`fieldBFS` 的距离小（0–6），**立成高度**跟工具① 的 `field` tab 呼应。

#### 9c 开工前定下的（2026-08-09）

上面那段只说了「扩既有返回值、零新钩子优先」，没说具体怎么做。真开工前把 `mark` 从算法一路量到渲染层，六条定在这里。**每一条都注明了是量出来的还是选出来的。**

**① 这道题是「车，但每步只走一格、只往右或往上」。**
`pathCount` 的移动规则规格原文没写；「帕斯卡三角到几千」钉死了只许右/上（8×8 空盘 = C(14,7) = **3432**）。摆**真的车**，与其余五题同一个身份。**而那条限制本身就是要教的**：车本来滑一整行，路径数是**无限**的（可以来回踏）；限成「一次一格、不往回走」，计数才有限——**「无环」正是动态规划能成立的前提**。tips 必须把这句说出来，否则它只是一道穿着棋盘外衣的格路题。她刚在 `rookCover` 里见过会滑的车，对照是现成的。

**② 标量走 `kind`：`mark(sq, ways)`，`kind` 从 `string` 放宽成 `string | number`。** ⚠ 量出来的
教学源码里直接写数字，不做字符串拼接（那份源码的读者是没学过棋的十六岁，一次 `"n" + ways` 就是一次噪音）。**页面层以下零改动**——这是量过的，不是估的：`interp.js` 的宿主包装层把 kind 原样塞进 boardOp（`{kind:'mark', sq, to: kind, from: …}`），`debugger.js` 的 `boardState` 原样读回（`marks[op.sq] = op.to`），撤销路径拿 `from` 的旧值回退——**没有任何一处检查它的类型**。

**这条的风险在另一头，而且是静默的**：`onMark(kind)` 返回 `null` 的种类**不画，也不报错**。数字若没被 `onMark` 接住，格子就是空的，全页照常绿。**这是 9c 唯一需要新立一道门的地方**（跟阶段 8 的「白名单空了」、9a 的「抛了就算过」是同一类：缺省行为是沉默）。

**③ 第三根轴是免费的：入口写成 `fillLayer(d)`，按反对角线层递归。** ⚠ 选出来的
z = 反对角线层号 `r + c`。同一层的格子互不依赖、**可以同时算**，下一层只依赖上一层——塔一层层长上去，看到的是「**为什么这个顺序可以填**」，而不只是「递推式长什么样」。这跟 `knightPath` 的 `expand(frontier, d)` **逐字同构**（那条声明的注释写着「第三根轴不需要任何额外声明就是对的」），所以 `zLabel` 之外不需要任何新机制。

**不选「行号」的理由写下来**：`z = r`（逐行填）跟教材里「一行一行填表」直接对应，但它只表达「我们选了这个顺序」，**看不出为什么这个顺序合法**——而后者才是 DP 的地基。

**④ 图例：`kinds` 的契约从「会用到的 mark 种类」改成「图例的行与顺序」。** ⚠ 这一条动的是六道题共用的声明层措辞
`kinds` 是**声明驱动**的（决定图例的行与顺序），不是扫描实际 mark 得来的——所以连续的数值域天然不会挤进图例。`pathCount` 取 `kinds: ['try', 'num']`，其中 **`'num'` 只用于图例那一行，算法从不发它**。

这让 `kinds` 原来那句「这道题会用到的 mark 种类」变成一句不实的话，所以**契约措辞要一并改**：「图例的行与顺序；**不要求每一行都对应一个真被发出来的 mark 值**——数值域那一类就是用一行代表整个域」。**一行文档改动，零代码改动**，另外五道题一个字不受影响。

**⑤ 墙与写字两样都是现成的。** ⚠ 量出来的
`board().blocked` 是阶段 7 为 `kingDominate` 扩的、已经画成斜纹墙，`pathCount` 直接用。「在格子上写数字」也不需要新渲染能力：`E.label3(C, [x,y,z], text, …)` 已存在，而 `board-render.js` 的 `drawCoordLabels` 正是拿 `squareCenter(f, r)` 在格子上画字。

**⑥ 9c 只实现「写数字」，但要跑一段「立成高度」的可行性探针。**
「只设计一次」欠的账是**标量怎么从算法到渲染层**，那一条由 ② 付清了。但 `fieldBFS`（9f）要的是另一种**呈现**——立成高度。9c 不实现它（自己用不上，而它的真实需求要到 9f 才看得清），但要**拿同一条数字通道跑一段探针**验证这条路走得通，探针**不落成工具、不进注册表**。

理由与 9b 那段位盘探针一样：**9c 是这笔账的付款人，而「设计完了、到 9f 才发现渲染层做不到」是这笔账最贵的失败模式**。探针要回答两个具体问题：**柱高取什么单位**（距离 0–6 的动态范围与盘面尺寸的关系），**值为 0 的格子怎么画**（0 是一个真实的答案，不是「没有值」）。

**→ 探针已经跑完，两个问题的答案定在本节末尾的「探针跑完的裁定（2026-08-09）」。9f 直接读那一节，不必回到这里。**

**9c 不做**：挖空（opt-in，不在本阶段）、`fieldBFS` 本身（9f）、数字按值上色成热力图（YAGNI——数字自己已经承载了信息）。

**声明层有三条硬约束，写错了整页停住**（阶段 7 Task 6 立的 `validateDecl` 三道门；三条都是先被人眼从截图里抓到、后来才补上门的）：

1. **`sources` 超过一份 ⇒ 必须自己声明 `sideView`。** 默认的 `3` 侧视沿世界 x 轴看进去，而并排的几块棋盘正是沿 x 轴摆开的——不换就完全重合（**并排那段位移在屏幕上投影为零**，几块盘的中心落到同一点；声明之后它们相隔两百来像素）而什么都不报。三次独立的对照实验量到的余数分别是 0.1 / 0.0 与一个一两像素的值——差别只来自量法、窗口与那一帧相机停在哪里，所以**这里刻意不写一个"实测像素数"**，那会是伪精度。`tourKnight`（阶段 5）与 `kingDominate`（阶段 7）各撞过一次。
2. **`onMark().label` 的显示宽度 ≤ 72、`trackLabel()` 的 ≤ 26**（CJK 算 2）。图例是 `position:fixed` 且没有 `max-width`，长了会整块钻到右上角面板底下；轨道标题画在每块盘底下、居中于盘心，长了两条的半宽一相加就撞在一起。两者都真的发生过（106 宽的图例 → 594.6 px，右缘压过面板左缘；31 与 28 宽的两条标题 → 224 + 202 px，两条的半宽和与两块盘盘心之间那点距离同一个量级）。**盘心之间那个数这里同样刻意不写**（与上一条同一个理由）：它随盘面档位、窗口大小与 `fit.s` 浮动，复现时量到的是 235–255 px 这样一个区间，没有任何东西钉住它——撞没撞是截图上看得见的，余量不是。
3. **一道题只能有一份「带挖空的」可编辑源码。** 存档键 `chess.exercise.v1.<题>.src` 与 `.<挖空 id>` 都只按题目名分。不声明 `exerciseSources` 的题目在练习模式下是「每一份源码都可编辑」，所以多份源码的题目将来加挖空时，必须同时在 `exerciseSources` 里把其余几份降成 `role:'contrast'`。

**这条可扩展性要求必须被真的验证过，而不是"看起来支持"**：阶段 5 的三题里，`knightPath` **最后加**，专门用来证明加一题确实只动这三处。如果加它时还改了别的地方，那就是架构没做到，要回头改架构而不是接受。

**相机按 §5.3 的常规条，不走工具④ 那条例外**：工具⑤ 的主体**就是一块棋盘**（八皇后摆的是真正的后，巡游走的是真正的马），所以 `1` 正视打头、`2` 桌面 45°。但 §5.3 同样要求：凡是把第三根轴立起来的 tab 必须另给一个沿那根轴的侧视——`queens` 的 z 是递归深度、`knightPath` 的 z 是 BFS 层数、`tourKnight` 的 z 是步序，三题都要。

#### 探针跑完的裁定（2026-08-09）

探针跑完了（`chess/core/algos/path-count.probe.test.js`：一条前置断言「数字确实通过 `mark` 通道送出来了」，加三条编号断言——宿主拿到的是可直接当高度用的有限**数值**而不是格式化过的字符串、**0 是被真的标出来的值**、同一条通道扛得住 `pathCount` 几千的量级）。⑥ 里那两个问题——**柱高取什么单位**、**值为 0 的格子怎么画**——的答案定在这里。**这一节是写给 9f 实施者的输入**，不是 9c 的记录：9f 要把 `fieldBFS` 每格的标量立成高度，下面两条不必再重新裁一遍，也不该再当成开放问题。

**两条结论的依据都不是推理出来的，而是仓库里已经这么干了。** 工具① `chess/tools/chess-moves-geometry.html` 的 `drawHeightField()`（`:2594`）就是「每格一个标量立成柱子」的既有实现，distance field / mobility / metric 三个 tab 都在用它（`:2816`、`:2859`、`:2894-2895`）。**9f 应当照抄它，而不是另起一套**——下面两条各自附了照抄时的偏移量。

**裁定① 柱高是 `z = k · value` 的世界坐标（不是像素），`k ≈ 2.8 / 该场的值域上限`。**

工具① 把这个比例算过**两遍**，两遍都落在 2.8：

```js
const K_FIELD = 0.35;      // :2628  注释：8 步的场高约 2.8，与棋盘边长 8 比例协调
const K_MOBILITY = 0.1;    // :2636  注释：改用 2.8 / 27 ≈ 0.1
```

`0.35 = 2.8 / 8`（BFS 步数最高约 8），`0.1 ≈ 2.8 / 27`（机动性最高 27，后在中心）。**「2.8 / 值域上限」不是一条被推导出来的公式，是同一个工具里两个量纲各自量了一次、得到同一个天花板。** 而且它的**失败模式也记在注释里**：mobility 若沿用 0.35，塔高会到 9.45，三倍于棋盘边长——所以这两个常数是**手写两个、刻意不合并**的（注释原文：「不要为了『统一』把它并回 `K_FIELD`」）。9f 若有多个场，照这个办：一个场一个常数，各自按自己的值域上限算。

**为什么是世界坐标而不是固定像素高度**：`:2599` 写的是 `const top = [base[0], base[1], k * d]`，`k * d` 是 z 分量，之后走 `E.line3` / `E.proj` 的透视投影。固定像素高度既做不到跨视角保持比例（转一下相机柱子就不对了），也拿不到正确的遮挡与前后关系。柱高因此以**格宽为单位**：工具① 的盘是 `BR.layout({ files: 8, ranks: 8, cell: 1 })`（`:2494`），`cell = 1`，所以「2.8 个世界单位」就是「2.8 格」。

⚠ **照抄那行时要改一个地方：工具① 写的是 `k * d`，不是 `base[2] + k * d`。** 工具① 的棋盘 `z` 恒为 0（`BR.layout` 没传 `z`），所以两者等价；工具⑤ 今天也是 `BR.layout({ …, cell: 1, z: 0 })`（`chess/tools/chess-board-algorithms.html:9678`）。但 `BR.layout` 是**接 `spec.z` 的**（`chess/core/board-render.js:19`，`const z = (spec && spec.z) || 0`；工具③ 的历史局面正是靠它沿 −z 分层，`:15-18` 的注释写着这个字段为什么在 layout 上而不在调用方）。**9f 写成 `base[2] + k * d`**，否则哪天棋盘离开 z=0 平面，柱子会整片留在原地而不报错。

⚠ **另一条边界**：那个 2.8 是照**边长 8** 的盘定的（注释原话「与棋盘边长 8 比例协调」）。工具⑤ 的盘面尺寸是滑杆参数，`fieldBFS` 若跑在明显更小的盘上，值域上限之外还要再看一眼盘的边长——**这一条工具① 回答不了，它只有 8×8**。

**裁定② 值为 0 的格子贴地画一格；而工具① 的既有公式天然如此，不需要额外分支。**

`drawHeightField` 的每格逻辑（`:2596-2606`）：

```js
const d = fieldObj[sq];
if (d === undefined) { E.solidDot(Cam, base, 2.5, 'rgba(148,163,184,0.45)'); return; }
const top = [base[0], base[1], k * d];
E.line3(Cam, base, top, …);      // line3 就是两点 strokePoly
E.glowDot(s, 4.5, '#ffffff', mid);
E.label3(Cam, top, String(d), …);
```

- `d === 0` → `top` 与 `base` 重合 → 线段退化成零长（`chess/core/viz-engine.js:273`：`line3 = (C, a, b, o) => strokePoly(C, [a, b], o)`，两点投影到同一个屏幕点，画出来什么都没有），辉光点落在地面上，标签写 `"0"`。**这就是「贴地画一格」，一行分支都不用加。**
- `d === undefined`（从没标过 / 够不到）走**上面那条 early-return** → 一个 2.5 半径的暗灰小点，无线、无标签。

**两种情形天然长得不一样**（白色辉光点 + 一个 `"0"` 字 vs 暗灰小点、无字），所以「0 是一个真实的答案，不是『没有值』」这件事在画面上是分得开的——这正是 ⑥ 提的那个问题。探针②（`path-count.probe.test.js`）验的是通道那一头：`mark(sq, 0)` 确实作为数值 0 送到宿主，不会退化成缺席。**两头合起来才成立：通道送得出 0，渲染画得出 0 与「没有」的区别。**

顺带一条 9f 用得上的：`drawHeightField` 把同排/同列的顶点用 `strokePoly` 连成网格，不可达格返回 `null` 当断点（`topOf()`，`:2607-2612`）——**0 值的格子网格是连过去的**（它有值，网格在那里探到地面再抬起来），`undefined` 的格子网格是断开的。这个区别与上面那条是同一条设计。

#### 9d 开工前定下的（2026-08-09）

§4⑤ 的表里 `bitboard` 只有一行「用 64 位整数表示棋盘，位运算生成走法」。地基（BigInt 与 `& | ^ ~ << >>`）9b 已经铺好，9c 的位盘可行性探针也验过子集够用（`1n << BigInt(sq)`、`b & (b - 1n)`、popcount 循环、64 位铺满七条差分全绿）。真开工前把这道题的形状与一处集成风险定在这里。

**① 这道题是「马的走法生成」。**
把整块盘当**一个** 64 位数，左右移位八次、每次配一张掉线掩码，一次算出所有马的攻击格。摆**真的马**（`place(sq, 'wN')`），攻击格走 `mark`。

选马不选王，是因为**文件回绕**在马身上最触目惊心：偏移量 15/17/6/10 会跨一到两条线，a 线上的马左移一下就落到 h 线去了。选它的代价是马在这套工具里已经出现过三次（巡游 / 最短路 / 9e 的独立集），但那三道题的**范式**互不重复（回溯 / BFS / 位运算 / 回溯剪枝），而 §4⑤「四道题的裁定」当初担心的是范式重复、不是棋子重复。

**② 教学落点就是文件回绕，而它只在「没有掩码」时才看得见。**
这是位盘唯一真正难的地方，也是「一个数就是一整块盘」这件事的代价：**移位不认识棋盘的边**，它只认识那 64 个二进制位排成的一条线。

**裁定：掩码写在源码里（完整正确的一份），`tips` 直接叫她把掩码那几行删掉、再 Run 一次。** 不加滑杆开关、源码里不带 `if (USE_MASK)` 这类人造分支。

⚠ **掩码不止一张，也不止两张**：马的八个偏移量是 ±6 / ±10 / ±15 / ±17，其中 ±15/±17 跨**一条**线、±6/±10 跨**两条**线，所以要分别防「a 线」「a+b 两线」「h 线」「g+h 两线」四种回绕。**具体几张、怎么命名归实施计划定**，但 `tips` 里必须点名到「删哪几行」而不是含糊的「删掉掩码」——她要能照着做。

理由是这个工具的立身之本（§2.8）：**她动手改这段源码、看着结果跟着变**。一个人造开关会让这份源码不再是「真引擎就这么写的」那一份，而那正是它的全部卖点。代价明写：**这一课靠她真去做**——所以 `tips` 要把「删哪两行、Run 之后看哪里」说到可以照着做的程度，不能只说「试试看」。

**③ 入口 `addDir(k)` 按方向递归，第三根轴因此是免费的。**
`addDir(k)` 处理第 k 个方向、末尾调 `addDir(k + 1)`，于是调用深度 = 第几个方向。这与 9c 的 `fillLayer(d)`（按反对角线层递归）、`knightPath` 的 `expand(frontier, d)`（按 BFS 层递归）是同一个做法，`zLabel` 之外不需要任何新机制。

⚠ **塔是九层，不是八层**（2026-08-10 实测订正）。本节初稿写的是「深度塔恰好八层 = 马的八个走法」，**那是数错的**：`addDir(k + 1)` 是**无条件**尾调，所以 `addDir(8)` 真的被调用、真的压一帧，进去之后才被 `if (k >= 8) { return; }` 弹回来。`TreeModel.build(trace, 'addDir')` 实测 **9 个节点、depth 0..8、每层 1 个**（sq = 0 / 27 / 63 三格各测一次，结果相同）。

**这个数是验收判据，所以订正它是必要的**：照初稿的「必须是八层」去验，一份**完全正确**的实现会被判不通过。真正的判别点不是 8 与 9 之差，而是**九层 vs 一层**——把尾递归换成外层 `for` 循环，塔会塌成 8 个节点全在 depth 0（实测），那才是这道题唯一要拦的东西。

**顺带一个白得的好处**：回绕的错**落在具体某一层上**——按 `3` 切侧视，哪个方向漏了掩码一眼可见。**这比「盘上多了几个格」信息量大得多**：她看到的不是「有 bug」，是「第 5 层那个方向有 bug」。

⚠ 与 9c 同一条已知缺口：**「递归还是循环」结果正确性测不出来**（9c 实测过：把 `fillLayer` 改写成外层 `for`，27 条单测照样全绿）。9d 同理，**唯一的守卫是浏览器验收里数塔的层数**——计划必须把这一条明写成「没有机器门」，别假装有。

**④ 参数与呈现。**
一个滑杆选马的位置（照 `knightPath` 的形状，`fmt` 显示 `a1`/`h8` 这样的代数记法），让她能把马拖到 a 线、h 线、角上，**看掩码真的在干活**——角上的马只有 2 个走法，中心的马有 8 个。

读数给两样：**攻击格数**（2–8，用 `b & (b - 1n)` 数出来，顺带教那个惯用法）与**位盘本身的十六进制值**——后者是让「这一整块盘就是这一个数」这件事在屏幕上有个落点。

**⑤ ⚠ 一处已实测的集成风险：`fmtInt` 会把 BigInt 印成「—」。**

这道题的 `run().result` 是一个 **BigInt**（攻击位盘）。而工具⑤ 的 `fmtInt`（`chess/tools/chess-board-algorithms.html`）第一行是：

```js
if (n == null || typeof n !== 'number' || !isFinite(n)) return '—';
```

实测：`fmtInt(3432)` → `"3,432"`，**`fmtInt(5n)` → `"—"`**。

**这与 9c 那条「`0` 不能被印成『—』」是同一类缺陷：把一个真实答案说成「不知道」。** 而这个工具全页的规矩是 `null` 才是「不知道」，绝不许在任何一处变成数字、也绝不许把数字变成它。

**裁定：读数里凡是要显示位盘值或任何 BigInt 的地方都不许走 `fmtInt`**，另写一条格式化路径（十六进制更合适——一个 64 位位盘的十进制值是 20 位数字，读不出结构；十六进制是 16 个字符、每字符正好一行）。

**已验过没问题的那一半**：`sameValue(a, b)`（Check 比结果用的，`chess-board-algorithms.html:6816`）第一行是 `if (a === b) return true`，而 `5n === 5n` 为真——**Check 路径不用改**。这一条写下来是为了让实施者不必再查一遍。

**9d 不做**：车/象的滑行攻击（要占据位图与 magic bitboard，量级完全不同，也不在 A-level 范围）、挖空练习（opt-in，不在本阶段）、两份源码对照（那是 `kingDominate` 的形状，这道题没有两个算法可比）。

## 5. 交互规格

### 5.1 全交互 + 自动演示是同一条时间轴

统一的传输控件（五个工具共用）：`播放 / 暂停 / 单步 / 步退 / 速度`。

**你不动它就自己走，你一落子它就停在你这一步。** 因此"全交互"与"自动演示"不是两种模式，是同一条时间轴的两种驱动源。

### 5.2 落子交互

- 点棋子 → 高亮其全部合法目标格（工具 ② 的 `legal` tab 同时用第二色显示伪合法但非法的格）
- 点目标格 → 落子；也支持拖拽
- 非法走法**当场拒绝并说明理由**，文案是具体的：`Illegal: your king would be in check from the bishop on g5`，而不是"不能这么走"
- 升变弹出四选一（含 underpromotion）
- `Ctrl/Cmd+Z` 撤销，走法栈支持任意回退与再分支

### 5.3 相机与快捷键

沿用设计系统 §5：拖拽旋转、滚轮缩放、右键平移、双击回第一个视角、数字键切视角预设、空格播放/暂停。棋盘特有：`F` 翻转棋盘视角（白方视角 ⇄ 黑方视角）。

**本子项目的视角次序与设计系统不同，这是一条有意的偏离**（2026-08-04 定）。设计系统要求 `views` 的第一项是 `iso`（斜转轴测），那条规则是为数学工具写的：那里第三根轴上有东西，斜过来才看得见。棋盘不是——斜转轴测把 a1–h1 那条边斜过来，行列读不出，八个格子数不清。所以：

| 键 | 视角 | 说明 |
|---|---|---|
| `1` | **正视** `az=0, el=0` | 每个棋盘 tab 的**第一项**：引擎的初始相机、双击回正的家。沿棋盘法线（z 轴）正对看进去。注意「正对棋盘」不是 `el→π/2`——棋盘铺在世界的 x–y 平面上，法线是 z |
| `2` | **桌面 45°** `az=0, el=−π/4` | 人坐在桌前看一副摆好的棋盘的角度。仰角**是负的**：`makeCam()` 的 `eye.y = dist·sin(el)`，`el>0` 会把 8 线（黑方）拉到近处、1 线推远，那是坐在黑方对面；`el<0` 才把白方放在自己面前 |
| `3`… | 轴测 / 侧视 | 排在其后。**凡是把第三根轴立起来的 tab（步数场、应手层、回合轴、博弈树深度），必须提供一个沿那根轴的侧视**，否则那一层结构在正视下是不可见的 |

唯一的例外是**不画棋盘、只画沿某根轴生长的曲线**的 tab（当前只有工具③ 的 `eval`）：正视等于顺着曲线看进去，什么也读不到，它的第一项仍是侧视。判据是「这一页的主体是不是一块棋盘」，不是「这一页有没有棋盘」。

调试器类工具（④⑤）尤其按此办：读代码的人同时要读棋盘，斜过来的行列是纯粹的负担。

### 5.4 调试器工具（④⑤）的额外交互

- 分栏可拖拽调宽；`\` 一键折叠代码面板回全屏棋盘（§1.5 的承诺）
- 单步 `F10`（步过）、`F11`（步入）、`Shift+F11`（步出）、`F9` 设/清断点、`F5` 跑到断点——沿用主流调试器的键位，这样她将来打开 VS Code 是同一套肌肉记忆
- **代码面板获得焦点时，上述快捷键仍生效，但方向键与文本编辑键归编辑器**
- 点棋盘上任一格 → 代码面板跳到最近一次操作该格的那一步（反向定位）

### 7.1 perft 参考值

`perft` 是国际象棋引擎的标准正确性测试：从某局面出发数第 N 层的合法走法叶子数，这些数字是公认定值。

| 局面 | depth 1 | depth 2 | depth 3 | depth 4 | depth 5 |
|---|---|---|---|---|---|
| 初始局面 | 20 | 400 | 8,902 | 197,281 | 4,865,609 |
| Kiwipete | 48 | 2,039 | 97,862 | 4,085,603 | 193,690,690 |

**必测**：初始局面 depth 5、Kiwipete depth 4，另加若干专攻边界的已知局面（吃过路兵导致的双重别子、易位穿过受攻格、升变吃子带将）。

**perft 不过，后面五个工具全是错的**——尤其是易位权、吃过路兵、升变这些边界，人眼根本查不出来，而 perft 一跑就露馅。这是本仓库第一个有标准答案可对的验收门（现有 61 个工具的门槛只有 `node --check`）。

### 7.2 棋谱正确性

棋谱取自公开历史记录，不凭记忆敲。真正的保障是：**每一局在加载时都由合法走法生成器逐步重放**，任何抄错的一步都会当场走不通并报错。

这挡不住"合法但抄成了另一局"，因此额外核对**总步数与结果**是否与公认记录一致。两个数字一起对上就基本锁死。

### 7.3 解释器正确性：拿 JavaScript 自己当参照实现

`interp.test.js` 对每个测试程序，把**同一份源码**同时交给自写解释器和原生 `Function(...)`，比对返回值与日志序列。任何不一致即失败。

这是一个格外强的门——参照实现就是 JavaScript 本身，不需要人工写期望值。测试集覆盖：算术与短路求值、数组操作、`for`/`for…of`/`while` 与 `break`/`continue`、函数与闭包、**深递归**（回溯算法的核心）、以及六道算法题的完整运行结果。

另有一组**语法错误定位测试**：给定坏代码，断言报错的行、列与消息类别正确——因为编辑器的实时检查全靠它。

### 7.4 挖空练习的正确性

一道挖空题可能坏在两个方向：**永远判对**（判定太松，随便填都过）或**永远判不对**（判定太严，正确的别种写法被判错）。两者都会让功能形同虚设，而且不测就发现不了。

因此每个声明的挖空必须通过三项断言：

1. **参考答案通过自己的判定**——听起来是废话，但 `check` 声明写错时它就不成立
2. **至少一个已知错误变体被判错**，且分歧步定位在预期位置（±0 步，精确匹配）
3. **至少一个"正确但写法不同"的变体被判对**——这一项专门防判定过严，是三项里最容易漏写、也最重要的一项

第 3 项要求每道挖空题在测试里附一份等价改写。写不出等价改写的挖空，说明这个位置只有唯一写法，不适合做成练习——**这条约束本身就是挖空选点的筛子**。

### 7.5 双语源码的正确性（阶段 8 加）

双语源码坏起来的方式与文案不同：**它会静默地把两种语言变成两套算法**。手滑在英文版里少写一个 `- 1`、或者把 `<` 改成 `<=`，读中文的人和读英文的人从此在学不同的东西，而屏幕上一切正常——两边各自都能跑。

所以不靠人眼比对，靠两道机械门：

1. **代码同一**：把两种语言变体各自**抽掉注释、并把每个字符串字面量替换成同一个占位符**，剩下的字节必须完全相同。这道门只放过注释与字符串的差异，别的一律拦下。
2. **步数同一**：同一道题、同一组参数，两种语言下解释器跑出的 `trace.length` 必须相等。注释不产生步；一次 `log` 无论字面量多长都是一步。第一道门万一被某种巧合绕过，这道门从行为侧再拦一次。

3. **行数同一**：两种语言变体的行数相等（§1.6 的逐行对齐不变式）。这一道其实被①蕴含（①要求抽掉注释后逐字节相同，而注释是整行的），但**单独报出来**——它是最容易违反、也最容易一眼看懂的那一条，混在①的「字节不同」里报等于没报。

三道门都写进 `check.py`（第五道门那一族，跟着源码走），对**每一份带 `lang` 的 `algos/*.js`** 逐份执行。

另有一道**只在阶段 8 内跑**的临时门，不进 `check.py`：**中文变体与改动前逐字节相同**。这一阶段不许动中文——中文一个字节不变，六个文案任务的 diff 就只剩「新增的英文」，审查看得完；哪天真发现中文哪句写错了，停下来报告，单独处理。基线取阶段起点那个 commit 的 `git show`，不落盘成夹具（否则将来改中文会被自己的门挡住）。

第一道是**结构**判据、第二道是**行为**判据，**两道各自都有对方才拦得住的漏**：

- ①过②不过：`①` 把字符串一律换成占位符，于是它默认「字符串只喂给 `log`」。真要有人写 `if (label === '皇后')`，两种语言下就是两条不同的分支——①看不见，②当场步数对不上。
- ②过①不过：把 `i < n` 写成 `i <= n - 1`，同一行、同样步数，却是两份不同的源码。

**两道门都不管英文说得对不对**——「英文与中文讲的是不是同一件事」机器判不了，那是每个文案任务的人工审查项（见 §8 阶段 8）。门守的是「代码没有偷偷分岔」，不是「翻译没有走样」。

### 7.6 断言的判别力（阶段 9a 加）

`_test.js` 的 `throws(fn, label, pattern)` 第三个参数是可选的，**不传就退化成「抛了就算过」**。全仓实测（2026-08-07）：**149 条 `T.throws` 里 84 条没有第三参，占 56%**，集中在四个文件——`exercise.test.js` 44、`chess-core.test.js` 17、`interp.test.js` 12、`tree-model.test.js` 8（合计 81/84）。

**但补上 pattern 也可以是恒真的。** 阶段 7 栽过一次：三条错误消息共享前缀 `source({ W, H, blocked }) 少了 …`，于是 `/W/`、`/H/`、`/blocked/` 三个 pattern **匹到了每一条**，把那三道守卫全删掉仍然四条全绿。

所以这道门守的是**判别力**，不是有无：

> 对每一条 `T.throws`，拿同文件里**别的** `T.throws` 实际抛出的消息去试它的 pattern。**一个匹上全部消息的 pattern 等于没有。**

84 条人肉互试不现实，所以 9a 的产出之一是一个**普查脚本**：跑一遍捕获每条的真实消息，再用每条的 pattern 横扫，报出「匹中率 = 100%」的那些。它让「补 pattern」从一件靠自觉的事变成一道门。

**这道门为什么排在阶段 9 的最前面**：9b 要大改 `interp.js`，而 `interp.test.js` 现在有 12 条恒真的 `T.throws`。在没有门的情况下改共用核心，失败模式是**安静的**。

### 7.7 BigInt 与位运算的正确性（阶段 9b 加）

9b 给解释器加 `& | ^ ~ << >>` 六个运算符与 BigInt。**判据不是「六个运算符能跑」，是差分矩阵**：每个运算符 ×（Number, BigInt, 混用）三种操作数，逐一跟原生 `Function(...)` 对拍——**包括该抛的那些必须同样抛**。

**混用那一档是这道门的重点。** JS 里 `1n + 1` 抛 `Cannot mix BigInt and other types`，而教学源码里 `sq` 下标是数字、位盘是 BigInt，**必然混用**。解释器**不许自动转换**：§7.3 那道差分测试拿 JavaScript 自己当参照实现，任何语义分歧都会让它当场作废——**而它作废的方式是安静的**（两边都「跑通了」，只是答案不再是同一个答案）。

顺带记下这一改会碰到的既有约定：

- **`interp.test.js` 有 6 条测试断言这六个运算符被拒绝**（各查 category 为 `'unsupported'` 且消息点名该运算符）。9b **要删掉它们**——子集边界移动了，这是正当的，但必须写明是「边界移动」而不是「测试挡路」。
- **`_test.js` 的 `eq` 两边都走 `JSON.stringify`，而 `JSON.stringify(1n)` 抛 TypeError**（约束 7 那条老规矩正好撞上）。要加 BigInt 的 replacer。
- **`>>>` 不加**：它对 BigInt 在 JS 里本来就抛，位盘也用不着。少一个运算符就少一条要跟原生对齐的语义。⚠「不加」指的是**不进子集**，不是「不给诊断」——它照旧要报一句点名 `>>>` 的 `unsupported`，见下面「探针跑完的裁定（2026-08-08）」。
- 轨迹的 `deepCopy` **不用动**——它是手写递归、不走 JSON，BigInt 作为原始值直接过。

#### 9b 开工前定下的（2026-08-08）

上面那几条是阶段 9 拆节时写的方向。真开工前把 `interp.js` 与原生行为各跑了一遍，**七件 §7.7 原文没写、其中两件会静默出事**的事定在这里。

**① BigInt 的入口是两个：`123n` 字面量与 `BigInt(x)` 内建，都要。**
9d 的位盘两样都躲不掉：掩码要写 `1n`，而 `sq` 是数组下标、必然是 Number，要移位就得 `BigInt(sq)` 转一次。**「必须显式转」正是这一课要让她撞上的东西**，把转换挪到另一头（整条链路都用 BigInt、下标再 `Number(...)` 转回去）只是换个地方付同样的账。原生行为实测：`0x1Fn` / `0o17n` / `0b101n` **合法**，`1.5n` / `1e3n` / `01n` 是 SyntaxError——四条数字通道各自吃一个可选的 `n`，拒绝的形状跟原生逐一对齐。

**② `checkNumTail` 必须先认 `n` 再检查——这笔债从「顺手」变成「硬的」。**
它今天见到 `1n` 会当成「数字字面量后面紧跟标识符字符」直接毙掉。阶段 9a 的账本本来只是提醒 9b「顺手收紧 `interp.test.js:168/170/176` 三条共用的 pattern」，现在 BigInt 字面量把这一处变成必改。**同时补裸 `0o`/`0b` 用例**——9a 预告过：那一刻某些被放宽到该形状的 pattern 会突然被第九道门判钝，**那是预期，不是回归**。

**③ `BINOP` 是重排不是追加。** ⚠
JS 真实优先级里位运算夹在 `&&` 与相等之间、移位夹在关系与加减之间，所以整张表要从今天的六层变成十层（`||`:1 `&&`:2 `|`:3 `^`:4 `&`:5 相等:6 关系:7 移位:8 加减:9 乘除:10）。**重排会动到已有表达式的解析结果**，不是往表尾加五行那么无害——差分测试必须专门覆盖混合优先级（`1 | 2 & 3`、`1 << 2 + 3`、`a & b === c`），而不只是覆盖新运算符自己。

**④ `Update`（`++`/`--`）会静默漂类型。** ⚠
`interp.js` 的 `Update` 分支写的是 `Number(old) + 1`，而 **`Number(1n)` 不抛、返回 `1`**——于是 `let x = 1n; x++` 得到 Number `2`，原生是 `2n`。两边都「跑通了」，只是类型不再是同一个类型，正是 §7.7 开头说的那种作废方式。改成按类型分支。**那一行上方「本子集没有 BigInt，不需要分支」的注释同时作废，要一起改掉**——一条声称「不需要」的注释留在需要它的代码旁边，比没有注释更坏。

**⑤ 六个运算符直接借原生实现，并写明这道门因此弱在哪儿。**
`applyBinary` 里 `case '&': return l & r;` 就够了：ToInt32、`>>` 的符号位、BigInt 任意精度、混用当场抛（连报错文字都跟原生逐字相同）全部白送，也不会跟参照实现分岔。**代价要写明**：借原生等于差分测试两边是同一个实现，那六格**必然通过**——它在这里验的不再是运算语义，而是**词法与解析有没有把 token 送到正确位置**（优先级、结合性、一元 vs 中缀）。别让人以为这道门在这一段比实际更有力。

这不跟本节开头「判据是差分矩阵」矛盾，是给它划边界：**矩阵真正承重的是「混用」那一档与③的优先级重排**（那两处的正确性来自我们自己写的词法/解析/分派，不来自原生），而「Number×Number」那一档基本是形式上的。**知道哪一格是白送的，才知道哪一格出错时要去看谁。**

**⑥ `eq` 的 BigInt 编码必须跟字符串区分得开，且这条区分本身要有断言守着。**
replacer 若把 `5n` 编成字符串 `"5"`（或 `"5n"`），它就跟字面字符串 `"5"`（或 `"5n"`）撞——**一撞就是「真不一致却判相等」的静默漏**，而 `eq` 是全仓每个测试文件的地基。用一个不可能与真实值重合的形状（如 `{"__bigint__":"5"}`），并在 `_test.self.test.js` 里把 `eq(5n, "5")` 与 `eq(5n, "5n")` 都必须判不等写成断言。**没有断言守着的编码选择，等于没选。**

**⑦ `debugger.js` 的 `fmtVal` 要在 9b 里补 `bigint` 分支。**
它今天没有这个分支，一个 BigInt 会掉到末尾的 `String(v)`——**`5n` 在变量面板上显示成 `5`，跟数字 5 一个样**，而 BigInt 在位盘里的全部意义就是「它不是 Number」。谁引入这个类型谁负责它怎么显示；留到 9d 就是让写位盘的人在面板上看见 `5` 时自己去猜。**代价是 9b 不再是「纯基建、零浏览器验收」**：改 `debugger.js` 要连带三份内联镜像（工具④⑤ + `_debugger-preview`），得加一条浏览器勾选项。这个代价是明知故犯的。

**收尾：9b 以一段位盘可行性探针结束，而不是以「六个运算符能跑」结束。**
一段真的位盘代码走 `diff()`：`1n << BigInt(sq)`、`b & (b - 1n)`、`popcount` 循环、`0n` 当循环条件、`b.toString(2)`、`log()` 打 BigInt。探针**不落成工具、不进注册表**，就是一条差分测试。它要回答一个明确的问题：**`&=` `|=` `^=` `<<=` `>>=` 五个复合赋值要不要进 9b**（词法器今天没有它们，§7.7 只点了六个运算符，YAGNI 说别加；但若位盘代码满屏 `b = b & (b - 1n)` 难读，那就是加的理由）。**先跑再定，不预先裁。**

理由跟阶段 8 拿 `queens.js`（最小的一份）先验「逐段等行数写不写得成」是同一个：9b 唯一的客户是 9d，而**「加完六个运算符、到 9d 才发现子集还差点什么」是这一段最贵的失败模式**。

**数字分隔符 `1_000n` 不加**：原生支持，但本子集连 `1_000` 都不支持，9b 不在这儿扩边界。

#### 探针跑完的裁定（2026-08-08）

探针跑完了（`chess/core/interp.test.js` 末尾「位盘可行性探针」一段：七条位盘写法的 `diff()`、两条轨迹存活断言、两条子集边界的 `T.throws`；七条 `diff()` 全绿，子集足够写位盘）。上面那句「**先跑再定，不预先裁**」到此为止 —— **两条结论定在这里**，9d 不必再去别处找，也不该再把它当成一个开放问题。

**探针① 五个复合赋值 `&= |= ^= <<= >>=` → 不进子集；但必须各有一句 `unsupported` 的诊断。**

不进子集的理由有两条。频次那条：`b = b op (...)` 这个形状在探针里**只出现两处**（popcount 循环的 `b = b & (b - 1n)`、建掩码循环的 `b = b | (1n << BigInt(sq))`），不是上面假设的「满屏」，翻盘条件没被满足。可读性那条更硬：对着一个刚学会位运算、**还没见过复合赋值语法**的十六岁学生，`b = b & (b - 1n)` 比 `b &= b - 1n` 更直白 —— 它不要求她先学一条新语法糖（「`&=` 是 `&` 和赋值的合体」），只是重复了她已经认识的 `=`、`&`、变量名。五个新词法记号换来的只是省掉几次对 `b` 的重复输入，用量对不上引入成本。

⚠ **限定（最终审查追加，9d 必须连着这一条一起读）**：那个「只出现两处」的计数**取自七条互不相连的探针片段，不是一份完整的位盘源码**。而本节原文把「频次/可读性」立成了**唯一的翻盘条件** —— 也就是说这个计数正好落在承重的位置上，却是从一份有取样偏差的样本上数出来的。**9d 写出真正的 attack table / move generator 之后，若发现 `b = b op (...)` 远不止两处（比如同一个函数体里就四五次），本裁定要重开**，不需要另找理由。可读性那条论证不依赖这个数，所以结论今天仍然成立 —— 但它的第二条腿是虚的，别当它是实的。

**这个问题还有第三个选项，而它才是真正落地的那个：不进子集，但给一句 `unsupported` 的诊断。** 探针报告只在「加/不加」两项里选，漏了它，于是 9b 短暂地留下了一个退化：这五种写法原先靠 `UNSUPPORTED_BINOP` 里的 `& | ^ << >>` **顺带**被拦成「不支持」（`b &= 1n` 词法成 `&` + `=`，`&` 当场报错），六个运算符进子集之后那条顺带的拦截没了，五种写法**静默降级成 `syntax`**。而它们都是合法 JavaScript：`syntax` 等于对使用者说「你写的不是 JavaScript」。更糟的是这里有一处**不对称会让她主动撞上** —— 这个子集**支持** `+= -= *= /= %=`，她刚用 `n = n + 1` 写完 popcount，试着写 `b &= b - 1n`，得到的却是一句说她语法错了的话。

落地形状是 `interp.js` 的 `UNSUPPORTED_ASSIGN` 表（跟 `**=` 逐字同构，每条都给出替代写法）：

```
Unsupported syntax: the &= operator (use x = x & y instead) (line 1). This interpreter supports a subset of JavaScript.
```

`>>>` 走同一条路（`PUNCT` + `UNSUPPORTED_BINOP`，报 `the >>> operator (unsigned right shift)`）。⚠ **这不跟上面那条「`>>>` 不加」矛盾**：「不加」指的是**不进子集** —— 算不出结果、不必跟原生对齐一条语义；这里加的是**诊断**。`**` 就是这个处境的现成先例：它在 `PUNCT` 里、在 `UNSUPPORTED_BINOP` 里，而它不被支持。**「不实现」与「不给诊断」是两件事，这个子集一贯只做前者。**

**探针② `b.toString(2)` → 不加。**

自己写循环约多 6 行（结果变量 + 零值特判 + 取最低位 + 右移），而**那 6 行恰好在复习刚教过的移位与掩码** —— 跟 popcount（`b & (b - 1n)`）、取位（`(b >> BigInt(sq)) & 1n`）是同一族操作的变体，重复一次是巩固而不是负担。且这套引擎真正的可视化通道是 canvas 棋盘格，不是一行 01 字符串：打印二进制串更像开发者的调试便利，不是这一课要教的东西。

最硬的那条理由是最终审查补的（比上面两条都硬，因为它跟成本大小无关）：`getProp` / `resolveCallable` 一律以 `typeof obj === 'object'` 为闸门，而 BigInt 是**原始值**。要让 `b.toString(2)` 通，就得**给原始类型开一条新的属性解析通道** —— 那不是「多支持一个方法」，是给整个子集换一个属性模型，并且立刻要回答 `(5).toFixed(2)`、`"a".length`、`arr.map` 该不该跟着开。**这一条不因用量变化而翻盘，跟①那条限定不同。**

**顺带提醒 9d**：不加 `toString(2)`，加上 `log()` 对 BigInt 走 `String(msg)`，两件事合起来意味着**位盘在文本侧完全没有可读表示**（`log("b = " + b)` 打出来是一长串十进制数字，看不出哪一格亮着）。**演示要压在棋盘格上**，别指望文本输出 —— 这跟设计系统「canvas 是主角」那条原则是一致的，不是将就。

两条裁定各自的探针在 `chess/core/interp.test.js` 的「位盘可行性探针」一段末尾（`T.report()` 之前），注释里分别标着「探针①」与「探针②」。

## 9. 明确不做的事（YAGNI）

- **不做棋力引擎**。工具 ④ 的 minimax 只为讲清搜索，评估函数保持两项、可解释；不追求棋力。
- **不做在线对弈、账号、云端存档**。
- **不做开局库、残局库**。
- **解释器不追求完整的 JavaScript**。§2.6 的子集就是全部范围；不支持的语法在解析阶段明确报错，不做"尽力而为"的部分支持——半懂不懂的解释器比明确拒绝更危险。
- **编辑器不做自动补全、格式化、多文件、语言服务**。高亮 + 行号 + 断点 + 语法检查，够用即止。
- **练习模式不做计分、评级、进度条、成就**。它是自学工具不是考试；随时可看答案（§2.9）。存下的尝试次数只为将来做"哪些概念反复卡住"的回顾视图，不用来评判她。
- **不支持带变着（variations）与注释的复杂 PGN**。只支持主线 + 标准标签对。遇到变着时跳过并提示，而不是报错退出。
- **不在阶段 0–3 内实现 3D 棋子模型**。只留可替换接口与性能预算。
- **不修改 `outputs/` 下任何现有工具，不改 `tools.json` / `app.html` / `sync_registry.py`**。对主站的唯一改动是在 `index.html` 加一个指向 `chess/index.html` 的入口链接（阶段 1，一处，不触碰其 `TOOLS` 数组，因此不影响 `sync_registry.py --check`）。
