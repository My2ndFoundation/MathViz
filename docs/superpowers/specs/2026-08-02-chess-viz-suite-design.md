## 0. 目标与受众

**受众**：16 岁，国际象棋**完全零基础**，即将开始 A-level Mathematics、Further Mathematics、Computer Science。

**目标不是提高棋力**，而是一条三段式路径：

1. **基本目的**：快速学会国际象棋的完整规则——一两个晚上从零到"读得懂题面、看得懂棋谱"。
2. **中间环节**：通过观看经典棋局，把规则从"记住的条文"变成"理解的东西"。
3. **最终目的**：**看懂与国际象棋相关的 CS 算法题，并学会自己设计算法去解这些谜题。**

第 3 条是全套工具的终点，它决定了工具 ④⑤ 不是动画而是**可编辑、可单步的算法调试器**（见 §1.4、§2.6–2.8），并最终落在**挖空练习**上（§2.9）——前面所有环节都是"看"，那是第一次"做"。

贯穿三段的手段是可视化——目的之一就是**靠"看得见"把兴趣先提起来**。

这条路径决定了全部设计取舍：规则层要**快而全**（不做低龄化动画，做能查能自检的参考级工具）；算法层要**对着考纲打**，而且必须让她能动手改。

### 与考纲的对应关系

| 棋盘问题 | 对应知识点 |
|---|---|
| 骑士巡游 | 哈密顿路径、启发式（Warnsdorff）|
| 车的最小覆盖 | 二分图匹配、König 定理（Decision Maths）|
| 王的最小支配集 | 支配集、贪心与最优的差距 |
| 八皇后 | 回溯、剪枝、状态空间搜索 |
| 马的最短路 | BFS、无权图最短路 |
| 博弈树 + α-β | 递归、对抗搜索、最好/最坏情况复杂度 O(b^(d/2)) vs O(b^d) |
| 王的移动距离 | 切比雪夫距离 L∞ 范数 |
| 香农数 | 指数增长、组合爆炸 |

## 1. 关键设计判断

### 1.1 为什么这套工具值得用 3D 引擎做

国际象棋是离散的，没有连续参数可以拖滑杆。但每个工具都有一个天然的**离散时间轴**，与引擎既有的 z 轴同构：

| 工具 | z 轴 | 顿悟视角看到什么 |
|---|---|---|
| ① 走法几何 | 最少步数场 | 马的场不是平移不变的：正相邻恒 3 步，而对角相邻在中心是 2 步、在角上是 4 步 |
| ② 规则与将杀 | ply（半步）| 将死 = 所有分支在某一层全部消失 |
| ③ 棋谱回放 | 回合数 | 一整局棋是三维里的一条曲线 |
| ④ 博弈树搜索 | 搜索深度 | α-β 剪掉的体积肉眼可见 |
| ⑤ 棋盘算法 | 递归深度 / 步序 | 回溯树沿 z 生长又缩回 |

所以这不是"把棋盘硬塞进 3D 引擎"，是真的合得上。

④⑤ 的 z 轴还有一层特殊含义：**它就是调试器里调用栈的深度**。栈长出去、树往 z 方向生长，是同一件事的两种画法。

### 1.2 独立子项目，但复用引擎

棋的状态是**离散、有分支、要撤销**的，与数学工具那套"共享 state + 连续采样"的模型硬绑在一起只会互相拖累。因此代码独立。但 3D 渲染引擎、设计令牌、UI 组件、i18n、录制回放框架全部复用（拷贝并裁剪）。

### 1.3 录制格式就是 PGN

设计系统 §11 主张"存轨迹，不存种子"。PGN 恰是这条主张的教科书例子——它存的是每一步的真实走法，而不是"初始局面 + 随机种子"。因此本子项目的录制格式**直接采用 PGN**，导出的存档可以丢进 lichess 打开。

### 1.4 算法工具是一台调试器，棋盘是它的输出窗口

工具 ④⑤ 不是"算法的动画"。它们是**单步调试器**：左边程序在跑、当前行高亮、调用栈随递归长出又缩回；右边棋盘上对应的格子同时被标成"正在尝试 / 已确认 / 被剪枝 / 回溯撤销"。两边是同一时刻的两种视图，而**驱动方是程序**，不是预先编排的动画。

这一条决定了整套工具的终点。规则与棋局是"看懂别人写的"，调试器是"看懂机器怎么想的，然后自己写"。

### 1.5 一条被明确推翻的设计原则

设计系统第 2 条不可动摇原则是"canvas 是主角——全屏，所有 UI 浮在它上面，永不切分它"。左右分屏的调试器**直接违反这一条**。

**决定：在 `chess/` 子项目内推翻它，并写下理由。** 代码面板不是控制器，是第二个内容视图；让它半透明浮在棋盘上会两边都读不清。

本子项目自己的规则：

> 除算法调试器（工具 ④⑤）外，canvas 仍是主角。调试器工具采用可拖拽的分栏，并保留一键折叠回全屏棋盘。

这是本子项目第二条与主仓库不同的规矩（第一条是默认语言）。独立子项目本来就该有自己的规矩，但每一条都要写下来并说明理由。

### 1.6 默认语言为英文

与仓库惯例（中文默认）相反，本子项目**英文默认、中文可切**。理由：使用者要读的是英文 A-level 课程与英文算法题，术语（fork、pin、en passant、backtracking、pruning）也都是英文。中文界面下术语仍以英文并列显示（`别子 pin`）。

### 2.1 单一编辑源 + 机器同步

九处 `★` 是**唯一手改的地方**。`inline_core.py` 把它们注入每个 `tools/*.html` 的标记区间：

```
/* >>> GENERATED:CHESS-CORE */ … /* <<< GENERATED:CHESS-CORE */
/* >>> GENERATED:BOARD-RENDER */ … /* <<< */
/* >>> GENERATED:VIZ-ENGINE */ … /* <<< */
/* >>> GENERATED:GAMES */ … /* <<< */      （仅回放工具）
/* >>> GENERATED:INTERP */ … /* <<< */     （仅 ④⑤）
/* >>> GENERATED:DEBUGGER */ … /* <<< */   （仅 ④⑤）
/* >>> GENERATED:ALGOS */ … /* <<< */      （仅 ④⑤，算法源码以字符串内联）
```

这是照抄仓库现有 `scripts/sync_registry.py` 的纪律，同样接进 `.githooks/pre-commit` 与 CI。运行时每个 html 完全自足，`file://` 双击可用。

> 这看似重复，但正是本仓库的既有做法——那个 3D 引擎本身就在 61 个文件里各复制了一份。内核有单一编辑源、运行时各自独立，"单文件零依赖"没有被破坏。

`algos/*.js` 特殊：它们**不作为代码执行，而是作为字符串内联**，运行时交给 `interp.js` 解释。所以显示给使用者的源码与实际被执行的源码是同一份字符串，不可能漂移。

### 2.2 引擎裁剪

**保留**：轨道相机（球坐标 `az/el/dist` + 平移）、透视投影与近裁剪、全部绘图原语（`strokePoly` / `line3` / `glowDot` / `label3` / `drawGridXY` / `arrowAt` …）、设计令牌与配色、tab/滑杆/读数/折叠面板等 UI 组件、i18n 的 `t()` 机制、录制回放框架。

**改掉**：

| 原引擎 | 本子项目 |
|---|---|
| 连续时间积分 `theta += ω·dt` | 离散 ply 推进 |
| 共享 `samples` 环形缓冲 | **走法栈 + 局面栈**（要能撤销、要能分支）|
| 自定义存档格式 | **PGN** |

### 2.3 `chess-core.js` 接口

零依赖纯 JS，可由 `node` 直接加载（`module.exports` 与 `window` 双导出）。

```js
Position.fromFEN(fen)        // → Position
pos.toFEN()
pos.legalMoves()             // → Move[]（已过滤自杀走法）
pos.pseudoLegalMoves()       // → Move[]（未过滤，供工具 ② 的差集高亮）
pos.attacksFrom(square)      // → Square[]
pos.attackedBy(square, side) // → Square[]
pos.make(move)               // → 新 Position（不可变）
pos.inCheck(side)            // → bool
pos.status()                 // 'ongoing'|'check'|'checkmate'|'stalemate'
                             // |'insufficient'|'fifty'|'repetition'
Move.toSAN(pos)  Move.toUCI()
parseSAN(pos, s) parseUCI(pos, s)
parsePGN(text)               // → { headers, moves[], result }
writePGN(headers, moves)
perft(pos, depth)            // → number（测试用）
```

内部表示采用 **0x88**（越界检测是一次按位与，走法生成简洁且不易错）。`Position` 不可变，`make()` 返回新对象——这让工具 ④⑤ 的树搜索和回溯天然安全，不需要 unmake。

### 2.4 `board-render.js` 接口（参数化棋盘）

算法工具与前四个工具**共用同一套棋盘和同一套棋子**——八皇后摆的是真正的后，骑士巡游走的是真正的马。

```js
drawBoard(C, { files: 8, ranks: 8, origin, cell, coords: true, mask: null })
drawPiece(C, { piece, square, scale, alpha, facing })
```

- 默认 `8×8`；N 皇后 `files=ranks=N`，N ∈ [4, 12]；骑士巡游 `5×5 / 6×6 / 8×8`；博弈树用 `4×4` 简化盘
- 坐标标注随尺寸自适应（`a`–`h` 自动扩到 `a`–`l`）
- `mask` 预留给"带禁区的棋盘"这类变体题

### 2.5 棋子渲染：SVG 路径 → `Path2D` → Canvas

棋子用 **SVG 的 `d` 路径数据**书写（可在矢量工具里画，也可手写），运行时 `new Path2D(d)` 交给 Canvas 2D 绘制。既保留 SVG 的作者体验，又不引入任何外部文件或加载器。

现阶段每颗子画成**朝向相机的剪影** + 脚下一枚随棋盘做透视变换的圆盘。白方浅描边、黑方暗描边，任意视角都读得清，贴合示波器美学。

**关于将来上 3D 的诚实评估**（现在只留接缝，不留承诺）：

- WebGL + `.glb` 最"正统"，但同时打破两条底线——零依赖（要模型加载器）和 Canvas-2D 引擎（整套投影/绘图原语要重写）。不是小升级。
- 更现实的中间路：棋子除马以外全是**旋转体**，可把同一份 SVG 侧影绕竖轴车削（lathe）成低模，仍用 Canvas 2D 画。马需单独处理。
- 性能须老实算：32 子 × 12 边 × 10 段 ≈ 3800 面，Canvas 2D 路径填充在这个量级会掉到 30fps 以下。因此它更可能是"静态视角下的展示模式"，而非可边转相机边跑的常态。

**决定**：渲染器抽成可替换接口 `drawPiece(...)`，从第一天起记录性能预算 **32 子的单帧绘制耗时 ≤4ms（`getImageData` 强制光栅化后测量）**。是否升级、升到哪一档，等有真实数据再定。（性能预算最初写成"32 子 @ 60fps"，实测才发现这个判据量的是宿主刷新率而非绘制代码本身——30Hz 宿主上无论代码多快都过不了，144Hz 宿主上无论代码多慢都轻松过；改成绘制耗时后，判据才真正只随代码改变。）

### 2.6 `interp.js` — 可单步的 JavaScript 子集解释器

工具 ④⑤ 的核心。约 700–900 行，零依赖，可由 `node` 直接加载与测试。

**为什么自己写解释器，而不是用生成器打点**：使用者的最终目标是**学会设计算法**。生成器打点方案里，调用栈只能手工维护、没有真正的"步入"、而且她无法改代码重跑——都会在"我想自己写一个"那一刻卡住。解释器把这三样一次解决，并且屏幕上显示的是**她能直接复制进 `node` 跑的真 JS**，不是伪代码。

**支持的子集**：`let` / `const`、赋值、数字/字符串/布尔/`null`、数组字面量与索引、对象字面量与属性访问、一元与二元运算、逻辑运算与短路、`if/else`、`for`、`for…of`、`while`、`break`/`continue`、函数声明与调用、`return`、**递归**、箭头函数、模板字符串。

**明确不支持**：`class`、`async`/`await`、`try/catch`、正则、`this`、原型链、解构、展开运算符。遇到不支持的语法在解析阶段就报明确的错（`Unsupported syntax: class declaration at line 12`），而不是运行到一半崩。

**实现方式**：解释器本身**用 JS 生成器写**（`function* evalNode(node)` + `yield*` 递归下降），每到一个语句边界 `yield` 一次。这样递归下降的写法天然可以在任意点暂停，代码量比手写显式栈机小得多，且不易错。

**宿主桥接**：算法通过一组内置函数驱动可视化——`mark(square, kind)`、`place(square, piece)`、`clear(square)`、`log(msg)`、`attacked(square)`。**这是算法与棋盘之间唯一的接口**，算法源码里看得见它们，所以使用者能明白"这一行为什么让那一格变了色"。

**快照策略**：每步记录**增量**而非全量（`{ line, frameOp, varDelta, boardOps, out }`），回放时正放前进、反放撤销。默认轨迹上限 **50,000 步**；超限则停止记录，并在读数区显式写明"已达上限，省略 N 步"——不静默截断。

### 2.7 `debugger.js` — ④⑤ 共用的调试器面板

| 区 | 内容 |
|---|---|
| 代码 | 当前行高亮；已执行过的行留淡色痕迹；点行号设断点 |
| 调用栈 | 帧列表，可点击跳到该帧。**栈深度就是该工具的 z 轴** |
| 变量 | 当前作用域的变量与值；本步变化的值闪一下 |
| 输出 | 每步一行日志（`try (3,5) → attacked by queen at (1,3)`）|
| 读数 | 尝试 / 回溯 / 剪枝次数、已用步数，与理论复杂度并列显示 |

**控制条**：`播放 / 暂停 / 单步 / 后退 / 步入 / 步过 / 步出 / 跑到断点 / 速度`。

"后退"能做到，是因为采用**先跑完、记全轨迹、再回放**的策略——单步、后退、拖时间轴、跳到任意步全部免费。这也正是设计系统 §11「存轨迹不存种子」在这里的应用。

**棋盘侧四种状态**各占一色（沿用 rose → violet → emerald → orange 顺序）：正在尝试 / 已确认 / 被剪枝 / 回溯撤销。

### 2.8 `editor.js` — 内嵌代码编辑器

代码面板**可编辑**。她能改算法、当场重跑、看棋盘上的结果如何变化。这是"学会设计算法"这个最终目的的落点：把 Warnsdorff 的启发式函数改成随便一个别的规则，巡游立刻失败——这一课比任何讲解都直接。

**零依赖下怎么做语法高亮**（不能用 CodeMirror / Monaco）：

采用**透明 `<textarea>` 叠在高亮层上**的经典做法——`<textarea>` 文字透明但光标可见，负责全部输入、选区、原生撤销、IME；底下一层 `<pre>` 渲染着色后的 token；两者字体度量完全一致、滚动同步。约 80 行，行为比自己实现 `contenteditable` 稳得多。

**高亮几乎不花额外成本**：`interp.js` 本来就需要词法分析器，编辑器**直接复用它**。因此高亮看到的 token 流与执行看到的是同一份——不存在"高亮说这是关键字、解释器说不是"的分歧。

**实时语法检查**：输入防抖后交给 `interp.js` 的解析器：

- 错误处波浪下划线，行号槽内红点，悬停显示消息
- 不支持的语法在此明确报出：`Unsupported syntax: class declaration (line 12). This interpreter supports a subset of JavaScript.`
- 有语法错时 `Run` 按钮禁用，不会跑到一半才崩

**其余编辑器行为**：行号槽（**断点也点在这里**）、当前执行行高亮（与调试器共用同一状态）、Tab 缩进、括号配对高亮。

**编辑后的流程**：改动 → 语法通过 → `Run` 亮起 → 重新解释执行、生成新轨迹 → 棋盘与调试器重置到第 0 步。

**安全与保护**：解释器天然是沙箱（子集里没有网络、没有文件系统、没有 `eval`）。真正需要防的是死循环——已有的 50,000 步轨迹上限同时充当执行上限，超限则停止并明确提示，而不是卡死页面。

**持久化**：改过的版本存 `localStorage`（按题目键），并提供 `Reset to original`。另提供 `Export .js`——导出的文件她可以直接在 `node` 里跑，因为那本来就是真 JS。

### 2.9 `exercise.js` — 挖空练习与差分定位

这是"最终目的"的落点。前面所有工具都是**看**，这是第一次**做**。

#### 挖空怎么声明

直接写在 `algos/*.js` 里，用注释指令圈出：

```js
// >>> BLANK level=1 hint="这一格会被已放置的皇后攻击吗？"
if (cols[c] || diag1[r + c] || diag2[r - c + N]) return false;
// <<< BLANK
```

**参考答案就是那份正在运行的源码本身**，不是另写一份。练习模式下这一段被替换成占位符与提示；正常模式下它就是被执行的代码。**因此两者不可能漂移**——这与 §2.1 里算法源码"显示与执行同一份字符串"是同一条纪律。

三级难度：`level=1` 填一个表达式（条件、返回值）；`level=2` 填一整个语句块；`level=3` 填一整个函数（给签名与注释）。

#### 怎么判对：比行为，不比文本

**绝不比对源码文本**——同一个条件有无数种正确写法。

判定方式是**跑她的版本和参考版本，比对可观测行为**。这几乎不花额外成本，因为解释器本来就要跑，而且轨迹本来就要记。

比什么由每道题自己声明，避免"正确但写法不同"被误判：

```js
check: { result: true, boardOps: true, counters: ['solutions'] }
```

例如 N 皇后里，一个不同写法但正确的 `isSafe` 会给出完全相同的解序列，所以 `boardOps` 可比；但若挖的是剪枝顺序相关的部分，就只比 `result` 与解数，不比步序。**这一条必须逐题显式声明，不能有默认值**——默认值会悄悄地把正确答案判错。

#### 判错时给什么：定位到第一处分歧

"错了"是没用的反馈。因为两个版本的完整轨迹都在手上，可以做到更好的事：

> **找出她的版本与参考版本行为分歧的第一步，把调试器直接跳到那一步，两边并排显示。**

她看到的是"跑到第 47 步为止你和参考完全一致，第 48 步参考认为 (3,5) 安全、你的版本认为不安全"——而不是一个红叉。这是这个功能真正的价值，也是它值得单独成一个模块的原因。

#### 提示分级，且随时可以放弃

提示逐级给，不一次给完：文字提示 → 点明涉及了哪几个变量 → 参考答案的结构骨架（保留控制流、挖掉表达式）→ 完整答案。

**任何时候都可以直接看答案并继续。** 这是自学工具，不是考试；卡住而无法前进只会让她关掉页面。

#### 持久化

每个 `(题目, 挖空)` 的作答存 `localStorage`，含尝试次数与用了第几级提示——这样以后想加"哪些概念她反复卡住"的回顾视图，数据已经在了。

## 4. 五个工具

配色沿用设计系统：一条曲线一个颜色，按 rose → violet → emerald → orange 固定顺序，同一颜色在六处复用（图例点、曲线体、投影虚线、头部辉光点、读数粗体值、公式标签）。每个工具第一个视角必须是 `iso`（双击回家），并有一个正交的"顿悟视角"。

### ① `chess-moves-geometry` — Geometry of Movement

**顿悟**：每个棋子就是一组向量规则；而"控制中心"是可以量出来的数，不是口号。

| tab | 内容 |
|---|---|
| `piece` | 选棋种、点格子放子，实时高亮攻击域。这是学走法的地方 |
| `field` | **最少步数场**（z = 步数）。马的场最反直觉，且**不是平移不变的**：正相邻（同行或同列）全盘恒为 3 步；对角相邻只取 2 或 4 —— 中心是 2 步，角上却要 4 步（a1→b2）。无限棋盘上马的距离场平移不变，是 8×8 的边界把它掰断了 |
| `mobility` | 机动性高度场：每种棋子在 64 格各自能攻击几格。骑士中心 8 格、角上 2 格 |
| `metric` | 距离度量：王 = 切比雪夫距离 L∞、车 = 两步内可达全盘。A-level 范数的具象版 |

**顿悟视角**：`field` tab 的正交俯视 + 侧视对照——俯视看覆盖形状，侧视看阶梯高度。

### ② `chess-rules-check-mate` — Rules, Legality and Mate

**顿悟**：合法走法 = 伪合法 ∩ 不自杀。将死不是一种特殊状态，是"合法走法集合为空且正被将军"。

| tab | 内容 |
|---|---|
| `legal` | 伪合法 vs 合法**同屏双色高亮**，差集正好是被别住的子（pin）。整个工具最关键的一页 |
| `special` | 易位（四个前提逐条亮灯）、吃过路兵（含"只在下一步有效"的时间窗）、升变（含 underpromotion）|
| `check` | z = ply：展开对手所有应手，全部落空 = checkmate；无合法走法但未被将军 = stalemate |
| `mate` | 基本杀法 K+Q vs K、K+R vs K。学会走棋后第一件真正能做到的事 |

易位的四个前提在 `special` tab 逐条以指示灯呈现：王未动过、该车未动过、之间无子、王的起点/路径/终点均不受攻击。

### ③ `chess-game-replay` — Reading a Game

**顿悟**：一局棋是三维里的一条曲线。

| tab | 内容 |
|---|---|
| `board` | 播放条 + SAN 步表，历史局面沿 z 堆叠 |
| `trace` | **子力轨迹**：每颗子沿 z 的三维折线。一眼看出"这只马走了 9 步，那只象一步没动" |
| `eval` | 沿回合的三条曲线：子力差（rose）/ 控制格数（violet）/ 王的安全度（emerald）|
| `heat` | 整局累计热力：哪些格是战场，哪些从头到尾没人碰 |

**输入**：30 局预置（内联，保证 `file://` 可用）+ PGN 文件拖入 + FEN 粘贴。

**王的安全度**定义（须明确，否则实现会各写各的）：己方王周围 8 格中被对方攻击的格数，取负值；范围 [-8, 0]。这是一个粗糙但可解释的指标，工具内会说明它粗糙在哪。

### ④ `chess-search-minimax` — Game Trees and Search

**顿悟**：α-β 剪掉的体积是肉眼可见的一块；而香农数说明为什么永远剪不完。

**采用分屏调试器布局**（见 §1.5、§2.7）：左边是 minimax / α-β 的真实源码在单步跑，右边是博弈树。走到 `if (beta <= alpha) break;` 那一行时，树上整片枝子同时塌掉。

| tab | 内容 |
|---|---|
| `tree` | 纯 minimax，z = 搜索深度，值逐层回传。调试器的调用栈就是树上的当前路径 |
| `prune` | 同一棵树开 α-β：被剪的枝染灰塌陷，读数 `访问节点 12,438 → 1,207` |
| `order` | 走法排序的威力：随机序 vs 吃子优先序，剪枝率差数倍——**O(b^d) 与 O(b^(d/2)) 的实物证明** |
| `shannon` | 分支因子 35 的指数爆炸 vs 可观测宇宙原子数（此 tab 无调试器，是纯图表）|

**用简化棋盘**：树画得下的前提是局面要小。采用 `4×4` 简化盘与若干残局局面，而非开局全盘。这一点已与使用者确认。

评估函数保持**可解释的简单**：子力值 + 中心控制，两项，都能在读数区看到分解。目的不是下得好，是让人看懂搜索。

### ⑤ `chess-board-algorithms` — Classic Problems on the Board

**顿悟**：同一块棋盘，是全部经典算法范式的共同舞台；而算法不是魔法，是一行一行跑出来的。

同样采用分屏调试器布局。棋盘尺寸随题目而变（§2.4），棋子用的是真棋子——八皇后摆的是真正的后，骑士巡游走的是真正的马。

**阶段 5 首批六题**：

| 键 | 题目 | 范式 | z 轴 | 可调 |
|---|---|---|---|---|
| `queens` | N 皇后 | 回溯 + 剪枝 | 递归深度——栈长出又缩回 | N ∈ [4,12]；解数 2/10/4/40/92/352/724/2680/14200 |
| `tourDFS` | 骑士巡游 · 朴素 DFS | 回溯 | 递归深度 | 5×5 / 6×6 / 8×8，起点可选 |
| `tourWarnsdorff` | 骑士巡游 · Warnsdorff | 贪心启发式 | 步序 1→N² | 同上；与 `tourDFS` 同屏对比 |
| `knightPath` | 马的最短路 | BFS | BFS 层数 | 起点、终点 |
| `rookCover` | 最少 8 车覆盖全盘 | 二分图匹配 + König 定理 | 增广路轮次 | 棋种、盘面 |
| `kingDominate` | 最少 9 王支配全盘 | 贪心 vs 精确，差距可见 | 选取轮次 | 盘面 |

`tourDFS` 与 `tourWarnsdorff` 并列的意义：**同一个问题、同一块盘、两份可以逐行对比的源码**，一个指数一个近线性。这是"算法设计"这件事本身最直观的一课。

**阶段 6 扩展题目**（架构已支持，届时只加键）：

| 键 | 题目 | 范式 |
|---|---|---|
| `bitboard` | 用 64 位整数表示棋盘，位运算生成走法 | 位运算——真实引擎的做法，正好压中 A-level 位运算 |
| `pathCount` | 棋盘路径计数（含障碍）| 动态规划 |
| `independent` | 最大独立集（互不攻击的最多同种子）| 回溯 + 剪枝 |
| `fieldBFS` | 多起点 BFS 生成整张最少步数场 | 与工具 ① 的 `field` tab 呼应 |

**可扩展性（明确的架构要求）**：

```js
const PROBLEMS = {
  queens: {
    label, params,                  // 滑杆声明，UI 自动生成
    source: ALGOS['queens.js'],     // 被解释执行、也被显示的同一份字符串
    entry: 'solve',                 // 入口函数名
    board: st => ({ files: st.N, ranks: st.N }),
    onMark(kind, square) { … },     // 宿主桥接的可视化语义
    readout(trace) { … },
  },
  tourDFS: { … }, …
}
```

新增一道题 = 加一个键 + 一个 `algos/*.js`；tab、滑杆、调试器面板由 UI 自动生成。

## 5. 交互规格

### 5.1 全交互 + 自动演示是同一条时间轴

统一的传输控件（五个工具共用）：`播放 / 暂停 / 单步 / 步退 / 速度`。

**你不动它就自己走，你一落子它就停在你这一步。** 因此"全交互"与"自动演示"不是两种模式，是同一条时间轴的两种驱动源。

### 5.2 落子交互

- 点棋子 → 高亮其全部合法目标格（工具 ② 的 `legal` tab 同时用第二色显示伪合法但非法的格）
- 点目标格 → 落子；也支持拖拽
- 非法走法**当场拒绝并说明理由**，文案是具体的：`Illegal: your king would be in check from the bishop on g5`，而不是"不能这么走"
- 升变弹出四选一（含 underpromotion）
- `Ctrl/Cmd+Z` 撤销，走法栈支持任意回退与再分支

### 5.3 相机与快捷键

沿用设计系统 §5：拖拽旋转、滚轮缩放、右键平移、双击回 `iso` 视角、数字键切视角预设、空格播放/暂停。棋盘特有：`F` 翻转棋盘视角（白方视角 ⇄ 黑方视角）。

### 5.4 调试器工具（④⑤）的额外交互

- 分栏可拖拽调宽；`\` 一键折叠代码面板回全屏棋盘（§1.5 的承诺）
- 单步 `F10`（步过）、`F11`（步入）、`Shift+F11`（步出）、`F9` 设/清断点、`F5` 跑到断点——沿用主流调试器的键位，这样她将来打开 VS Code 是同一套肌肉记忆
- **代码面板获得焦点时，上述快捷键仍生效，但方向键与文本编辑键归编辑器**
- 点棋盘上任一格 → 代码面板跳到最近一次操作该格的那一步（反向定位）

### 7.1 perft 参考值

`perft` 是国际象棋引擎的标准正确性测试：从某局面出发数第 N 层的合法走法叶子数，这些数字是公认定值。

| 局面 | depth 1 | depth 2 | depth 3 | depth 4 | depth 5 |
|---|---|---|---|---|---|
| 初始局面 | 20 | 400 | 8,902 | 197,281 | 4,865,609 |
| Kiwipete | 48 | 2,039 | 97,862 | 4,085,603 | 193,690,690 |

**必测**：初始局面 depth 5、Kiwipete depth 4，另加若干专攻边界的已知局面（吃过路兵导致的双重别子、易位穿过受攻格、升变吃子带将）。

**perft 不过，后面五个工具全是错的**——尤其是易位权、吃过路兵、升变这些边界，人眼根本查不出来，而 perft 一跑就露馅。这是本仓库第一个有标准答案可对的验收门（现有 61 个工具的门槛只有 `node --check`）。

### 7.2 棋谱正确性

棋谱取自公开历史记录，不凭记忆敲。真正的保障是：**每一局在加载时都由合法走法生成器逐步重放**，任何抄错的一步都会当场走不通并报错。

这挡不住"合法但抄成了另一局"，因此额外核对**总步数与结果**是否与公认记录一致。两个数字一起对上就基本锁死。

### 7.3 解释器正确性：拿 JavaScript 自己当参照实现

`interp.test.js` 对每个测试程序，把**同一份源码**同时交给自写解释器和原生 `Function(...)`，比对返回值与日志序列。任何不一致即失败。

这是一个格外强的门——参照实现就是 JavaScript 本身，不需要人工写期望值。测试集覆盖：算术与短路求值、数组操作、`for`/`for…of`/`while` 与 `break`/`continue`、函数与闭包、**深递归**（回溯算法的核心）、以及六道算法题的完整运行结果。

另有一组**语法错误定位测试**：给定坏代码，断言报错的行、列与消息类别正确——因为编辑器的实时检查全靠它。

### 7.4 挖空练习的正确性

一道挖空题可能坏在两个方向：**永远判对**（判定太松，随便填都过）或**永远判不对**（判定太严，正确的别种写法被判错）。两者都会让功能形同虚设，而且不测就发现不了。

因此每个声明的挖空必须通过三项断言：

1. **参考答案通过自己的判定**——听起来是废话，但 `check` 声明写错时它就不成立
2. **至少一个已知错误变体被判错**，且分歧步定位在预期位置（±0 步，精确匹配）
3. **至少一个"正确但写法不同"的变体被判对**——这一项专门防判定过严，是三项里最容易漏写、也最重要的一项

第 3 项要求每道挖空题在测试里附一份等价改写。写不出等价改写的挖空，说明这个位置只有唯一写法，不适合做成练习——**这条约束本身就是挖空选点的筛子**。

## 9. 明确不做的事（YAGNI）

- **不做棋力引擎**。工具 ④ 的 minimax 只为讲清搜索，评估函数保持两项、可解释；不追求棋力。
- **不做在线对弈、账号、云端存档**。
- **不做开局库、残局库**。
- **解释器不追求完整的 JavaScript**。§2.6 的子集就是全部范围；不支持的语法在解析阶段明确报错，不做"尽力而为"的部分支持——半懂不懂的解释器比明确拒绝更危险。
- **编辑器不做自动补全、格式化、多文件、语言服务**。高亮 + 行号 + 断点 + 语法检查，够用即止。
- **练习模式不做计分、评级、进度条、成就**。它是自学工具不是考试；随时可看答案（§2.9）。存下的尝试次数只为将来做"哪些概念反复卡住"的回顾视图，不用来评判她。
- **不支持带变着（variations）与注释的复杂 PGN**。只支持主线 + 标准标签对。遇到变着时跳过并提示，而不是报错退出。
- **不在阶段 0–3 内实现 3D 棋子模型**。只留可替换接口与性能预算。
- **不修改 `outputs/` 下任何现有工具，不改 `tools.json` / `app.html` / `sync_registry.py`**。对主站的唯一改动是在 `index.html` 加一个指向 `chess/index.html` 的入口链接（阶段 1，一处，不触碰其 `TOOLS` 数组，因此不影响 `sync_registry.py --check`）。

| 风险 | 应对 |

| 走法生成器有隐蔽 bug | perft 是硬门；不过不进阶段 1 |
