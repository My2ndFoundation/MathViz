## 1. 段的定义（数据与门）

**段 = clean 文本里从本段 `from` 那一行起、到下一段 `from` 之前为止的全部行**（最后一段到文本末尾，含结尾换行）。
`to` 是本段**最后一个非空行**的整行原文——它存在的理由是让作者写清「这一段到哪为止」、让门能核对「段与段之间只有空行」。

为什么不直接用 `from`…`to` 的闭区间：段与段之间通常隔着空行，而空行不是唯一行、不能当锚；闭区间会让那些空行不属于任何段，
她临摹完全部段、拼起来却少了几个空行，复制出去的程序与原文不同。**「到下一段 `from` 为止」让段首尾相接、覆盖全文、拼回去逐字节等于 clean 文本**——
这正是 §4.3「片段拼回去必须与原文逐字节相同」在段这一层的版本。

**新门 `chunks_check`（D·库；门数 +1）**，只对声明了 `chunks` 的程序：

1. 形状：`chunks` 是数组、**至少 2 段**；每段 `title.en` / `title.zh` 非空字符串，`from` / `to` 非空字符串（锚本身的存在与唯一仍归 `anchor_check`）。
2. 顺序：在 clean 文本里 `from_k` 行号 ≤ `to_k` 行号 < `from_{k+1}` 行号。
3. 相接：`to_k` 与 `from_{k+1}` 之间只有空行；第一段 `from` 之前、最后一段 `to` 之后也只有空行（通常第一段 `from` 就是第 1 行的文档串）。
4. **JS 与门一致**：门在 node 裸 `vm` context（浏览器分支）里调页面内联的 `PyInteract.chunkSegments(clean, chunks)`，
   断言段数、每段起止偏移与门用 Python 算出的一致，且各段 `text` 拼接 === `clean` 文本。（「门验的与 UI 用的不是同一个解析」是第 0 期 `anchor_check` ① 付过的代价。）

每段行数（简报说 games 每段 20–40 行）**只是取向，不进门**——一个 45 行的 `main()` 硬拆成两段更糟。

负控制（实现时逐条做）：段锚写错一字 → `anchor_check` 红；两段之间夹一行非空代码（不相接）→ `chunks_check` 断言红；只写 1 段 → 红；
`title.zh` 置空 → 红；把 `chunkSegments` 改成闭区间（丢空行）→ 第 4 条断言红。

## 2. core 的改动

### 2.1 纯函数（`interact.js` 导出，node 可测）

`chunkSegments(cleanText, chunks) → null | [{ index, title, start, end, text, fromLine, toLine }]`

- `chunks` 缺省、空数组或解析失败（锚找不到）→ **`null`**，调用方走今天的不分段路径。失败时不抛——页面宁可退回不分段，也不能白屏；门保证真实数据不会走到这一支。
- `start` / `end` 是 clean 文本的字符偏移；`text === cleanText.slice(start, end)`；各段首尾相接、`[0].start === 0`、`[last].end === cleanText.length`。
- `fromLine` / `toLine`（1 起）只供显示「第 31–58 行」。

### 2.2 临摹模式（`interact.js` 的 DOM 层）

**一段 = 一个 reference = 一个 Trace session。** `trace.js` **一行不改**：三层对齐、逐行同步、首次即正确、空闲剔除、溢出与行数差，都原样作用在「这一段」上。
这是本设计最重要的选择——分段不碰对齐引擎，§4.3 的不变量天然保持。

| 元素 | 行为 |
|---|---|
| 段条（仅临摹模式、仅有 `chunks` 时出现在顶栏） | 「段 2 / 4 · 绘制（第 31–58 行）」+ 每段一个按钮（标题；已完成的带 ✓）+「上一段 / 下一段」 |
| 影子层 / 输入层 | 只显示**当前段**的参考与她在这一段打的内容（不显示别的段——三层坐标系从段首起算，与今天完全同构） |
| 逐段结算 | 当前段打全对（`correct === total`）时：段按钮标 ✓，统计行显示这一段的正确率 / 速度 / 用时，出现「下一段 →」按钮（**不自动跳**——她可能想回看这一段） |
| 总结算 | 统计行在段的数字之后加一格「全程 k / N 段」。**N 段都在干净的 run 里打完**时，才按全程汇总写 progress：`accuracy = Σ(total − errors) / Σtotal`，`cpm = Σcorrect / Σ活跃时间`；写入的仍是 `{ bestAcc, bestCpm, at }`——**progress 的 schema 不变**，不需要迁移 |
| 「重来」 | 只重来**当前段**（清这一段的缓冲、开一个新 session）。整题重来走已有的三级清空 |
| resumed | 逐段判：某段的 run 创建时它的缓冲非空，这一段就是 resumed；**任何一段 resumed，全程成绩都不写 progress**（与今天「接着草稿打的这一遍不计」同一条纪律） |
| 模式切换 | 每段的 run 与今天一样跨模式存活（`reuseRun` 按 progId + 段 reference 判）；切回临摹落在上次所在的段 |
| 复制（临摹模式） | 各段缓冲**按段序拼接**——「临摹 = 她打的缓冲区」（§3.5）。她只打了前两段，复制出来就是前两段 |

### 2.3 草稿

- 分段程序的临摹草稿仍存在 `St` 的 `(id, 'trace')` 键下，值是 JSON：`{"v":1,"seg":k,"typed":["…","…",…]}`（长度 = 段数）。
- 不分段程序的草稿**仍是今天的纯字符串**，一字不变。
- 分段程序读到一个纯字符串（这一题是后来才加的 `chunks`，她以前按整段打过）→ 当作「没有分段草稿」，从第 1 段空白开始；
  旧字符串在她打下第一个字之前不被覆盖（不因为打开页面就丢掉她的东西）。段数与草稿里的数组长度不同（作者改了分段）→ 同样当作没有。
- `store.js` 不改（它只存字符串）；三级清空照旧按 `(id, 'trace')` 清。

### 2.4 不受影响的

- **读模式**：不显示段（§3.4「读模式不受影响」）。行注、行号、讲解面板照旧。
- **挖空模式**：不受影响——挖空是按空判定的，与段无关。
- **`chunks` 缺省**：所有新代码都在 `if (segs)` 分支里；`segs === null` 时走的是今天那几行原样不动的代码。
  验证：core 测试里对一个无 `chunks` 的程序断言 `chunkSegments` 为 `null`、`copyPayload('trace', …)` 与今天相同；
  活体验收时对照一页没有 `chunks` 的页面，临摹模式的 DOM（段条不存在）、草稿键值（纯字符串）、复制内容与合并前逐字节相同。

## 7. 评审修复轮补记（2026-09-30）

1. **段尾空行自动补齐**（评审 I1，控制方裁决）：段参考以空行收尾时（段间空行归前一段，C1），影子层看不见那几个空行，逐键打的人打不到「段完成」。
   `PyInteract.chunkTailFill(reference, typed)`：她打完本段最后一个非空行**并按下 Enter**（缓冲 = 参考去掉尾部换行 + 至少一个换行，余下只有自动缩进的空格、换行数不超过参考尾部），UI 把缓冲换成完整的段参考，照常 update、结算。只在插入时补（删除时补会让退格删不掉）。
   不在「缓冲刚好等于去掉尾部换行的参考」时就补：那样她打完最后一行习惯性按的 Enter 会多出一行。trace.js 不改。
2. **全程不记要说出来**（评审 I2）：`chunkResumedAny(runs, typed)`——某段 run 是 resumed，或某段缓冲非空却还没有 run，统计行就写明全程不计。

### 已知限制

- **分段草稿格式是单向的**（评审 m3，不修）。分段程序的临摹草稿存成 `{"v":1,"seg":k,"typed":[…]}`；不分段的读取路径（§2.4 要求它逐字节不变）只认纯字符串。
  所以：(a) 以后某个程序**去掉** `chunks`，或 (b) 浏览器缓存里的**旧版页面**（没有分段代码）读到新写的分段草稿时，那段 JSON 会原样出现在临摹输入框里。
  去掉一个程序的 `chunks` 时，要么让她清掉这一题的草稿（「清空本题」），要么先在 `loadDrafts` 的不分段路径里加一个识别这种 JSON 的分支——后者是改不分段路径，要单独评审。
  (b) 只在新旧版本交替的缓存窗口里出现；`tool-version` 是缓存键，升版之后旧页不再被请求。
